## Summary

Phase 04.3 should freeze the interface between Cloudflare public entry and `apps/supervisor-api`, not the app behavior after the request is already inside supervisor logic.

The clean shape is:

- Cloudflare public entry may admit, normalize, and forward requests to the public runtime origin
- `apps/supervisor-api` may assume a bounded set of runtime-facing invariants
- any forwarding, trace, timeout, cache, body-size, and streaming expectations stay at the `apps/*` boundary

The contract should explicitly say:

- what category of forwarding assumptions exist
- what runtime origin may assume about request identity vs trace identity
- how timeout budget and body-size concerns are treated
- whether caching is disabled or narrowly constrained for the public answer path
- that streaming expectations belong to the runtime seam, not package internals

**Primary recommendation:** make this a two-artifact phase: one canonical architecture note under `docs/architecture/`, plus one implementation-oriented handoff note in `.planning/` that freezes allowed assumptions and deferred implementation details.

## Phase Boundary

### Public entry edge owns

- external request admission
- edge-side forwarding behavior into the public runtime origin
- edge-side cache and body-size posture
- edge-to-origin request metadata projection

### Public runtime origin owns

- runtime interpretation of forwarded metadata
- timeout/streaming handling after request arrival
- health/readiness contract surfaced by `apps/supervisor-api`

### Core packages must not change

- `packages/contracts`
- `packages/supervisor-core`
- `packages/rag-specialist`
- `packages/retrieval-core`

## Contract Truths To Freeze

1. Public entry forwarding remains between Cloudflare and `apps/supervisor-api` only.
2. Request-id/trace propagation is a runtime seam and must not be confused with app-layer actor identity.
3. Cache semantics for the public answer path must be explicit and conservative at the edge boundary.
4. Timeout, body-size, and streaming expectations must be documented as runtime assumptions, not package behavior.
5. Health/readiness belongs to the runtime contract, not the specialist/retrieval contract.
