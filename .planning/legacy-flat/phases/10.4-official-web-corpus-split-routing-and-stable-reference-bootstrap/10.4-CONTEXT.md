# Phase 10.4: Official Web Corpus Split Routing And Stable Reference Bootstrap - Context

**Gathered:** 2026-04-05
**Status:** Ready for planning and execution
**Source:** Derived from the newly frozen `official_web` corpus-split architecture, current `muc_public_pages` bridge/runtime truth, and the current projection/import implementation limits

<domain>
## Phase Boundary

Phase 10.4 turns the newly documented `official_web` corpus split into executable repo truth.

Its job is intentionally narrower than "finish all official-web serving surfaces":

- add machine-checkable projection routing truth for the first split
- make replay/import able to work against routed `official_web` target scopes
- bootstrap the first downstream path for `official_web/stable_reference`

This phase is not the full fresh-news rollout.

### In Scope

- Introduce repo-tracked routing truth beyond `page_family -> one target_collection`
- Route the current stable-reference-like subset away from mixed `muc_public_pages`
- Keep replay output valid when different target collections appear under one official-web batch
- Allow scope-specific import of one routed target collection from a mixed replay output
- Preserve `muc_public_pages` as the current mixed bridge for everything not yet moved

### Out Of Scope

- Opening `official_web/stable_reference` or `official_web/fresh_news` for default query serving
- Live-search fallback or freshness gate implementation for news
- Automatically routing formal regulations and formal curriculum pages into `regulations/*` / `curriculum/*`
- Full multi-scope import/release automation for all routed official-web surfaces in one command
- Changing crawl host scope or scheduler cadence

### Success Shape

- The repo no longer relies on "all official-web pages land in `muc_public_pages`" as an implicit projection truth
- `official_web/stable_reference` has one explicit routing path from official-web replay output into scope-specific import
- `muc_public_pages` remains a bridge collection, but only for content not yet promoted into a dedicated downstream surface
</domain>

<decisions>
## Implementation Decisions

### Locked by current architecture
- `official_web` stays one source channel; routing happens after source-truth, not in collector crawl scope.
- `projection-declarations.json` alone is no longer sufficient to express the final corpus split, because `page_family` is too coarse.
- The first executable split should start with stable-reference routing, not with fresh-news serving enablement.
- Import must stay scope-explicit and fail-closed; one command should not silently replace multiple current-truth scopes.

### Locked by current worktree truth
- `muc_public_pages` currently remains the mixed bridge and local QC/release-candidate surface.
- `release_gate_required` is the only current subset that is already close enough to bootstrap `official_web/stable_reference`.
- `future_fresh_news_surface` is a handoff seed set, not a ready-to-serve collection.

### The agent's discretion
- The exact shape of the new projection-routing config file
- Whether scope-specific import is implemented by pre-filtering replay documents or by extending the importer contract
- The exact regression tests that lock the first routed split
</decisions>

## Specific Ideas

- Plan `10.4-01` should introduce one repo-tracked routing config that can override downstream target scope for specific official-web documents without breaking current projection replay.
- Plan `10.4-01` should at minimum route the stable-reference-like current gate into `official_web/stable_reference`.
- Plan `10.4-02` should make import scope-specific, so a mixed replay output can be imported into one target scope at a time without violating current single-scope refresh guarantees.
- Plan `10.4-02` should prove the first routed `stable_reference` path with focused tests and local verification.
