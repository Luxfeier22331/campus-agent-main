<task type="auto">
  <name>Task 1: Define the operations prefix and object-storage contracts</name>
  <action>Write down the per-run object-store layout under `campus_notices/operations/authenticated-notice-closeout/{run_id}/` (including `run-manifest.json`, `frozen-input.json`, `shard-plan.json`, `heartbeat/{shard_id}.json`, `milestones/*.json`, and `reconciliation/closeout-summary.json`), specify what each artifact must contain (bundle/manifest references, checkpoint plan, digest counts, milestone progress, reconciliation digest), and call out the async-safe S3 semantics (one-shot zero-byte uploads, idempotent object names, manifest immutability) that each shard/promoter will rely on.</action>
</task>

<task type="auto">
  <name>Task 2: Finalize staging table schema and invariants</name>
  <action>Document the `ingestion_closeout` schema: `closeout_runs` (run metadata, expected counts, bundle/manifest/object prefixes, state machine timestamps); `closeout_shards` (run_id+shard_id PK, state, notice_count, attempt, heartbeat_ts, last_digest); `closeout_notice_stage` (notice_id, shard, content/document hash, artifact manifest, ready boolean); `closeout_raw_asset_stage` (raw_asset_id, raw_version_id, object keys, upload status); `closeout_document_stage` (document_id, revision, canonical path, doc hash, ready flag); `closeout_milestones` (milestone name, target_count, completed_count, summary JSON); `closeout_promotions` (promotion_id, run_id, verification_digest, doc_scope_count, raw_asset_coverage, state). Include indexes on run_id, shard_id, and notice_id plus JSONB columns for manifest/resolution data to keep digests traceable.</action>
</task>

<task type="auto">
  <name>Task 3: Outline the async executor and single-promoter flow</name>
  <action>Sketch the planner/executor/promoter interactions: planner reads `run-manifest.json`, computes shard notice slices, persists `shard-plan.json`, and initializes `closeout_runs`/`closeout_shards`; shard executors run under `asyncio` with aiobotocore/psycopg async connections, emit heartbeat objects, write per-notice artifacts/manifest entries into staging tables, and never touch `documents/internal_notice`; the promoter watches `closeout_shards`, waits for completed state, replays staged manifests, copies artifacts to canonical `campus_notices/documents/internal_notice/...`, performs a deterministic `replace_scope`, writes `closeout_promotions` and `reconciliation/closeout-summary.json`, and emits final milestone state for each shard.</action>
</task>

<task type="auto">

  <action>Capture the ingestion-worker CLI surface that starts a run, lists runs, tails milestone heartbeats, and triggers the promoter; describe API arguments (bundle path, manifest, checkpoint plan, run_id, resume flags) plus status outputs (shard counts, last heartbeat, verification state). Lay out the verification steps—comparing staged notice/raw/document counts/digests against expected run metadata before `closeout_promotions` moves to `verified`—and note the tests needed (status CLI assertions, staged table contents after simulated shards, promoter rejects mismatched digests) so future implementation has concrete regression targets.</action>
</task>
