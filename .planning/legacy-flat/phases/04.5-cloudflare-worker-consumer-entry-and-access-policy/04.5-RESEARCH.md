## Summary

Phase 04.5 should freeze one narrow seam: the Cloudflare Worker becomes the only public consumer-entry shell for the public answer hostname, while `apps/supervisor-api` remains the only repo-owned public runtime ingress behind it. The Worker is allowed to make entry decisions, normalize request shape, and project runtime-boundary trust signals to the origin. It is not allowed to absorb supervisor routing, package contracts, retrieval policy, or Phase 5 actor/ACL/audit ownership.

Current Cloudflare docs support the exact runtime shape this phase needs. A Worker on a Custom Domain can be the public hostname entry, can clone/modify requests before forwarding, can use encrypted secrets for origin trust material, and can sit behind Cloudflare Access for authenticated-only mode. Cloudflare also explicitly documents that Access-protected Worker requests still require JWT validation in the Worker, and that Bypass weakens controls and logging. That matters here: authenticated mode should rely on explicit Access validation, while anonymous mode should be an explicit Worker-owned flag, not an Access-policy shortcut.

The biggest planning risk is accidental side entrances. `workers.dev` and Preview URLs are public by default when enabled, and Cloudflare’s docs are explicit that both can be Access-protected or disabled. If this phase says “Worker is the only public consumer entry,” the implementation handoff must treat `workers_dev = false` and `preview_urls = false` (or equivalent protected handling) as part of the boundary, not as optional cleanup.

**Primary recommendation:** Freeze 04.5 around a single rule set: `Custom Domain -> Worker -> trusted origin/apps/supervisor-api`, with two entry modes (`authenticated-only` and `anonymous-enabled`), explicit fail-closed behavior, and no claim that Worker identity equals `SupervisorRequest.actor`.

### Pattern 1: Worker As The Only Public Consumer Entry
**What:** The public answer hostname terminates at a Cloudflare Worker on a Custom Domain. The Worker is the only public consumer-entry shell. It forwards only to the public runtime origin that serves `apps/supervisor-api`.
**When to use:** Always for the public answer path in this phase.
**Example:**
```toml
# Source: https://developers.cloudflare.com/workers/configuration/routing/custom-domains/
[[routes]]
pattern = "answer.example.com"
custom_domain = true

workers_dev = false
preview_urls = false
```

### Pattern 2: Two Explicit Entry Modes
**What:** Freeze exactly two Worker entry modes.
**When to use:** Always.
**Example:**
```text
Mode A: authenticated-only
- Worker hostname is protected by Access.
- Worker validates the Access JWT.
- Worker forwards a trusted runtime-boundary projection to origin.

Mode B: anonymous-enabled
- Worker does not require end-user login at the edge.
- Worker still forwards only to the trusted origin.
- Anonymous allowance is controlled by an explicit Worker flag, not by loosening package contracts.
```

### Pattern 3: Worker-To-Origin Trust Is Runtime Trust, Not Actor Identity
**What:** The origin should trust that the request came from the Worker, not that the end user has final app-layer identity semantics. Any Worker-projected identity remains runtime-boundary material until Phase 5 defines `SupervisorRequest.actor`.
**When to use:** Always.
**Example:**
```text
Worker responsibilities:
- validate entry mode requirements
- attach request-id / trace context
- attach trusted origin-auth material

Origin responsibilities:
- reject requests missing trusted Worker-auth material
- continue treating actor/ACL/audit as deferred app-layer work
```

### Pattern 4: Fail-Closed On Missing Config Or Invalid Trust
**What:** Missing Access config, missing JWT, missing origin secret, or invalid mode configuration must deny the request. The system must not silently degrade to public-open origin access.
**When to use:** Always.
**Example:**
```text
If ACCESS_REQUIRED=true and JWT validation config is missing:
- Worker returns 403/401
- Worker does not forward to origin

If origin receives a request without Worker trust material:
- origin returns 401/403
- origin does not fabricate a fallback actor
```

### Anti-Patterns to Avoid
- **Access identity equals `SupervisorRequest.actor`:** 04.5 must not claim this. Current repo docs repeatedly defer actor mapping to Phase 5.
- **Origin treated as directly public:** The Worker is the public shell. The origin must not be documented as safely public-by-default.
- **`workers.dev` / Preview URLs left public:** That creates extra public entries and breaks the “only public consumer-entry shell” claim.
- **Anonymous mode via Access `Bypass`:** Cloudflare warns that Bypass disables Access controls and logging; it is the wrong abstraction for the public answer product path.
- **Provider types pushed into `packages/*`:** Cloudflare concerns stop at the Worker/runtime seam and `apps/supervisor-api`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Access JWT verification | Custom JWT crypto and JWK rotation logic by hand | `jose` + Cloudflare Access JWK endpoint | Cloudflare documents JWT validation and key rotation behavior; crypto mistakes here are high-risk |
| Public hostname attachment | Ad hoc DNS/origin dance around a Worker preview URL | Worker Custom Domain | Custom Domains are the documented production attachment model for Worker-hosted public entry |
| Secret storage in Worker code or config vars | Plaintext tokens in `vars` or committed files | Worker Secrets | Cloudflare explicitly distinguishes Secrets from normal env vars for sensitive values |
| “Public anonymous” implemented as a hidden policy loophole | Access Bypass as the product-mode toggle | Explicit Worker flag | Bypass removes security controls and logging; the product decision should be explicit in Worker behavior |
| Actor inference from edge headers | Edge-derived permanent app identity schema in 04.5 | Keep actor/ACL/audit deferred to Phase 5 | Repo architecture explicitly separates runtime access envelope from app-layer actor semantics |

**Key insight:** 04.5 is a boundary-freeze phase, not an auth-system phase. Use Cloudflare’s built-in primitives for entry, secrets, and JWT validation; use repo docs and `apps/supervisor-api` as the seam; defer app identity closure.

## Common Pitfalls

### Pitfall 1: Trusting Access Headers Without Validation
**What goes wrong:** The Worker or origin treats `Cf-Access-Jwt-Assertion` as trustworthy merely because it exists.
**Why it happens:** It is easy to assume Cloudflare-added headers are enough.
**How to avoid:** In authenticated-only mode, validate the JWT against the team JWK set and the application AUD.
**Warning signs:** Planning language says “Access adds headers” but never says “validate JWT.”

### Pitfall 2: Leaving `workers.dev` Or Preview URLs Public
**What goes wrong:** The system has additional public entrypoints besides the intended public hostname.
**Why it happens:** Cloudflare enables or infers these routes unless explicitly disabled or protected.
**How to avoid:** Make `workers_dev = false` and `preview_urls = false` part of the 04.5 checklist unless there is a documented protected exception.
**Warning signs:** The plan names a Custom Domain as the public entry but says nothing about preview URLs.

### Pitfall 3: Using Access `Bypass` As Anonymous Product Mode
**What goes wrong:** Anonymous mode becomes an infrastructure loophole with reduced controls and no Access logging.
**Why it happens:** Bypass looks like the easiest way to make a path public.
**How to avoid:** Keep anonymous mode as an explicit Worker-owned runtime flag and preserve origin trust separately.
**Warning signs:** Planning language says “anonymous” and “Bypass” in the same rule.

### Pitfall 4: Treating Worker Identity Projection As Phase 5 Completion
**What goes wrong:** Edge/runtime headers get mistaken for final `SupervisorRequest.actor` or retrieval ACL semantics.
**Why it happens:** The current `apps/supervisor-api` shell already maps actor context from headers, so it is tempting to freeze those headers as final identity.
**How to avoid:** Document Worker-projected identity as runtime-boundary material only; Phase 5 still owns actor mapping and audit closure.
**Warning signs:** New docs start naming actor claims or group semantics as final.

### Pitfall 5: Forgetting Fail-Closed Behavior On Mode Misconfiguration
**What goes wrong:** Missing secrets or contradictory flags accidentally open the path.
**Why it happens:** Edge logic often starts as a permissive proxy.
**How to avoid:** Make “deny on missing config” an explicit architecture rule and checklist item.
**Warning signs:** No documented response for “anonymous flag unset,” “missing JWT config,” or “missing origin auth secret.”

## Code Examples

### Validate Cloudflare Access JWT In A Worker
```javascript
// Source: https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/
import { jwtVerify, createRemoteJWKSet } from "jose";

const jwks = createRemoteJWKSet(new URL(`${env.TEAM_DOMAIN}/cdn-cgi/access/certs`));
const token = request.headers.get("cf-access-jwt-assertion");

await jwtVerify(token, jwks, {
  issuer: env.TEAM_DOMAIN,
  audience: env.POLICY_AUD,
});
```

### Clone And Modify A Request Before Forwarding

```javascript
// Source: https://developers.cloudflare.com/workers/runtime-apis/request/
const outbound = new Request(originUrl, request);
outbound.headers.set("x-worker-trace-id", traceId);
outbound.headers.set("x-origin-auth", env.ORIGIN_SHARED_SECRET);
return fetch(outbound);
```

## Open Questions

1. **Should origin trust be enforced by private connectivity or by shared-secret header validation?**
   - What we know: Cloudflare supports Worker secrets, Access token validation, and Tunnel-side protection.
   - What's unclear: Whether the eventual public origin will be private/Tunnel-only or publicly routable behind additional checks.
   - Recommendation: Plan 04.5 around a generic “trusted origin only” contract, and let implementation choose between Tunnel/private origin and shared-secret origin auth without changing package boundaries.

2. **Does 04.5 need any Python-shell code change, or is it docs-only?**
   - What we know: Current `apps/supervisor-api` supports bearer-only auth and header-derived actor mapping.
   - What's unclear: Whether 04.5 will merely freeze docs/handoff, or also add a minimal origin-auth mode for Worker-to-origin trust.
   - Recommendation: Default the phase to docs plus handoff. Only add Python changes if the plan decides origin fail-closed behavior must be codified now.

3. **What exact names should be used for anonymous flag and origin trust headers?**
   - What we know: The context explicitly leaves naming to planner discretion.
   - What's unclear: Final header/env names.
   - Recommendation: Pick names that emphasize runtime boundary semantics, not end-user identity semantics; avoid `actor`, `user`, or `acl` in 04.5 naming.
