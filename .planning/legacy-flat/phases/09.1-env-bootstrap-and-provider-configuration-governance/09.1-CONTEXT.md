# Phase 09.1: Env Bootstrap And Provider Configuration Governance - Context

**Gathered:** 2026-04-02
**Status:** Ready for planning
**Source:** PRD distilled from `docs/plans/env-bootstrap-and-provider-configuration-governance.md`, current repo env/bootstrap code, eval settings, tests, and the confirmed `LLM_API_KEY` live-accept blocker diagnosis

<domain>
## Phase Boundary

Phase 09.1 is an urgent insertion between Phase 9 and the existing placeholder Phase 10.

It does not revisit retrieval semantics, official-web topology, or app ownership. Its job is narrower and structural:

- freeze the long-term env/bootstrap boundary
- centralize provider precedence resolution
- replace weak missing-key failures with actionable diagnostics
- separate local `.env` convenience from deploy secret ownership

The immediate trigger is the current handbook live-accept blocker:

- the current worktree `.env` already contains `LLM_API_KEY` and related provider settings
- ad-hoc `uv run --all-packages python - <<'PY'` processes do not auto-bootstrap `.env`
- repo docs still contain one incorrect “fallback to root worktree `.env`” statement
- eval settings collapse multiple failure modes into `LLM_API_KEY is required`

The phase must turn that diagnosis into a stable repo contract instead of another one-off local workaround.

</domain>

<decisions>
## Implementation Decisions

### Locked architecture posture

- bootstrap belongs to repo-shipped entrypoints, not library code
- settings/resolvers may read process environment, but may not read `.env` files on their own
- local runtime truth is the current worktree or current app, not an implicit parent worktree
- deploy runtime truth is a real secret store, not repo-root `.env`

### Long-term bootstrap contract

- repo-shipped Python CLI entrypoints may call a shared bootstrap helper
- ad-hoc inline Python / REPL should remain non-bootstrap by default
- if a developer wants ad-hoc code to see `.env`, they must explicitly source it or call the bootstrap helper

### Long-term provider contract

- shared provider truth defaults to `LLM_*` and `EMBEDDING_*`
- eval may explicitly override via `EVAL_LLM_*` and `EVAL_EMBEDDING_*`
- provider precedence must be implemented once in shared code, not reassembled in each consumer
- model names remain chain-owned:
  - `EVAL_RAGAS_MODEL`
  - `EVAL_JUDGE_MODEL`

### Long-term diagnostics contract

- failing fast is correct
- the failure must explain what was checked
- the error model must distinguish:
  - missing secret
  - missing bootstrap
  - wrong surface ownership
  - malformed value
- diagnostics and doctor commands must not print raw secret values

### Explicitly rejected directions

- do not add silent fallback to root worktree `.env`
- do not add import-time `.env` side effects in `packages/evals` or other libraries
- do not patch only the error message while leaving provider resolution duplicated
- do not treat a local shell convenience as deploy truth

</decisions>

<workstreams>
## Proposed Workstreams

### Workstream 1: Freeze and align the contract

- remove the remaining fallback drift from docs
- record the target bootstrap/provider architecture in repo-tracked docs
- make Phase 09.1 explicit in roadmap/state instead of hiding this work under “just add the key”

### Workstream 2: Build a shared bootstrap and provider-resolution seam

- extend `packages/shared` with explicit bootstrap state and typed provider-resolution helpers
- centralize `EVAL_* > shared` precedence
- expose typed config errors with surface-aware diagnostics

### Workstream 3: Migrate current consumers

- migrate `packages/evals` settings to the shared resolver
- align repo-shipped Python entrypoints on the same bootstrap contract
- preserve the explicit non-bootstrap semantics of ad-hoc scripts

### Workstream 4: Add doctor and verification lanes

- add a doctor command for presence/source/precedence checks
- add focused unit tests for bootstrap behavior, precedence, and error reporting
- update relevant docs/runbooks to reflect the new contract

### Workstream 5: Separate local convenience from deploy governance

- document deploy-side secret ownership and environment isolation
- freeze the rule that `dev` / `staging` / `prod` use separate provider keys
- keep local sync helpers as convenience only, not runtime truth

</workstreams>

<verification>
## Verification Targets

- `uv run --all-packages python -m unittest tests.test_repo_env_bootstrap`
- `uv run --all-packages python -m unittest tests.evals.test_settings`
- targeted tests for any new shared config/bootstrap module
- repo-shipped eval/supervisor entrypoint tests that prove bootstrap occurs only in official entrypoints

Success means:

- current worktree `.env` is the only repo-root local bootstrap source
- no consumer silently falls back to a different worktree
- provider precedence is implemented once and reused
- errors explain checked keys and surface name without leaking secrets
- docs no longer claim root-worktree fallback

</verification>
