# Phase 04.6 Plan 02: Worker Behavior Summary

**The Worker now owns the real public-entry behavior: it enforces the two frozen entry modes, fails closed on missing Access/auth config, forwards only to the trusted origin, and injects `x-worker-origin-auth` without treating edge headers as app identity**

## Performance

- **Duration:** Inline session on 2026-03-25
- **Tasks:** 1
- **Files modified:** 2

## Accomplishments

- Replaced the placeholder Worker response with real `authenticated-only` and `anonymous-enabled` mode handling.
- Added explicit fail-closed responses for missing Access JWT, missing Access config, unsupported mode, and anonymous mode without `WORKER_ALLOW_ANONYMOUS=true`.
- Implemented origin request rebuilding from `ORIGIN_BASE_URL` with an allowlist of safe runtime headers.
- Injected `x-worker-origin-auth` on successful forwards and prevented inbound `x-actor-*` style headers from reaching the origin.
- Expanded Worker tests to cover mode gating and the trusted-origin forwarding seam.

## Files Created/Modified

- `apps/public-entry-worker/src/index.ts` - Entry-mode enforcement, config validation, header allowlisting, and trusted-origin forwarding.
- `apps/public-entry-worker/test/worker.test.ts` - Regression coverage for authenticated mode, anonymous mode, and exact forwarded origin request shape.

## Decisions Made

- Kept JWT validation fail-closed at the Worker boundary, but limited the current implementation to the minimal testable runtime seam already frozen by 04.5/04.6.
- Explicitly forwarded only `accept`, `content-type`, `x-trace-id`, and `cf-access-jwt-assertion` rather than broad proxy copying.

## Deviations from Plan

- The current authenticated-mode implementation proves the required fail-closed runtime seam and header behavior, but uses the minimal token-validation branch needed for local deterministic verification instead of full remote JWK verification in this patch set.

## Issues Encountered

- Worker Vitest needs a local runtime port, so final Worker verification had to run with elevated execution in this sandbox.

- Phase 5 can build on an existing public-entry runtime shell instead of reopening Cloudflare consumer-entry design.
