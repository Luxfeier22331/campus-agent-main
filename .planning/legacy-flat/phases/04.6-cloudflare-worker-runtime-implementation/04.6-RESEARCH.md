## Summary

Phase 04.6 should be implemented as a new runtime shell under `apps/`, with the Worker owning public entry policy enforcement and request forwarding on a Cloudflare Route, while `apps/supervisor-api` owns the trusted origin seam immediately behind it. The cleanest repo shape is a dedicated Worker app such as `apps/public-entry-worker`, not an expansion of `apps/supervisor-api` and not a new package under `packages/*`.

The minimum real implementation is two-sided:

1. a Worker runtime shell that validates entry mode, forwards only to the trusted origin, and injects explicit Worker-origin trust material;  
2. a minimal `apps/supervisor-api` auth/runtime update that rejects requests missing valid Worker trust material and keeps any Worker-projected identity as runtime-only context.

Current official Cloudflare guidance supports the exact mechanics needed here:

- use routes declared in Wrangler when a Worker fronts an existing origin application;
- disable `workers_dev` and `preview_urls` explicitly in config if the Worker must remain the only public entry;
- validate `Cf-Access-Jwt-Assertion` inside the Worker when Access fronts the Worker;
- use Worker secrets for sensitive values;
- use the Workers Vitest integration for local unit/integration tests.

Our updated repo truth now matches that Cloudflare-native shape: the public hostname stays on the existing zone/hostname, a Route sends matching traffic into the Worker, and the Worker proxies only to the trusted `apps/supervisor-api` origin. This keeps the Worker as the only public entry code path without forcing the Worker to become the final origin object for the hostname.

**Primary recommendation:** implement `04.6` as a dedicated Worker app plus a small origin-auth patch in `apps/supervisor-api`, using a Route-based Worker in front of the existing origin, with strict fail-closed behavior and no `packages/*` changes.

## Architecture Patterns

### Pattern 1: New Worker App Under `apps/*`
**What:** Create a dedicated Worker runtime shell under `apps/`, for example:

```text
apps/public-entry-worker/
├── package.json
├── tsconfig.json
├── wrangler.toml
├── src/index.ts
├── test/worker.test.ts
└── README.md
```

**When to use:** Always for 04.6.
**Why:** Repo truth says `apps/*` are runtime boundaries. The Worker is a runtime shell, not a capability package.

### Pattern 2: Two-Sided Runtime Implementation
**What:** Implement both halves of the seam:

- Worker side:
  - decide entry mode
  - validate Access JWT when required
  - normalize/forward request
  - inject trusted origin-auth header
  - reject on missing/invalid config
- Origin side (`apps/supervisor-api`):
  - validate trusted Worker-origin auth
  - reject missing/invalid Worker-auth material
  - continue treating actor/ACL/audit as deferred

**When to use:** Always if the path must truly run end-to-end.

### Pattern 3: Worker As Public Shell, Origin As Trusted Private-Intent Runtime
**What:** The Worker owns public entry. The origin is not treated as directly public even if it is still technically reachable on the network.

**Implementation consequence:** the Worker should be attached by Route to the public hostname and should forward only to a dedicated origin base URL configured in env, and that origin must reject requests that do not carry the shared trust material.

**Important inference from repo truth:** the fetch target must not point back to the public Worker hostname, or the implementation risks routing loops.

### Pattern 4: Header Allowlist, Not Raw Proxy Copy
**What:** Build a new outbound request to the origin and explicitly control which headers survive.

**Keep:**
- content type / request body semantics
- request correlation headers
- a small runtime-context projection if needed
- `X-Worker-Origin-Auth`

**Do not treat as final app identity:**
- Access identity
- Worker mode headers
- any Cloudflare/provider-specific headers

### Pattern 5: Runtime Config Must Be Explicit And Fail-Closed
**Recommended Worker env/secrets shape:**

```text
ORIGIN_BASE_URL=https://trusted-origin.example.internal
ENTRY_MODE=authenticated-only | anonymous-enabled
WORKER_ALLOW_ANONYMOUS=true|false
ACCESS_TEAM_DOMAIN=https://<team>.cloudflareaccess.com
ACCESS_POLICY_AUD=<aud>
ORIGIN_SHARED_SECRET=<secret>
```

The exact names can change, but the implementation should keep a single explicit anonymous-mode switch and one secret-backed origin trust mechanism.

## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Access JWT verification | Custom crypto / hand-parsed JWTs | `jose` plus Cloudflare Access certs endpoint | Cloudflare already documents this pattern; auth mistakes here are high-risk |
| Sensitive Worker config | Plaintext vars committed to repo | Worker Secrets | Cloudflare separates secrets from normal config for a reason |
| Worker runtime testing | Ad hoc Node-only request mocks that do not run in Workers runtime | Workers Vitest integration | Official local test path, closer to real runtime behavior |
| Public entry toggles | Hidden infra shortcuts or policy loopholes | Explicit Worker config flags | 04.5 requires explicit, reviewable runtime policy |
| Cloudflare concerns in contracts | New provider metadata in `packages/contracts` | Keep concerns in Worker app and API-shell auth/runtime code | Repo architecture explicitly forbids Cloudflare/provider drift into packages |

## Common Pitfalls

### Pitfall 1: Implementing Only The Worker Side
**What goes wrong:** The Worker forwards with a shared secret/header, but `apps/supervisor-api` still only accepts the old bearer path.
**Why it happens:** The Worker implementation looks “complete” in isolation.
**How to avoid:** Treat origin-auth acceptance in `apps/supervisor-api/src/campus_supervisor_api/auth.py` as part of 04.6, not as future cleanup.

### Pitfall 2: Reopening Actor Semantics In The Worker
**What goes wrong:** Worker-projected identity gets treated as final `SupervisorRequest.actor`.
**Why it happens:** The Worker is the first runtime component to see Access claims.
**How to avoid:** Keep Worker identity projection as runtime-boundary context only. Final actor mapping remains Phase 5.

### Pitfall 3: Leaving `workers.dev` Or Preview URLs Reachable
**What goes wrong:** The system has public side entrances besides the intended hostname.
**Why it happens:** These are easy to overlook during deploy.
**How to avoid:** Hard-code `workers_dev = false` and `preview_urls = false` in `wrangler.toml`, and verify them in tests/review.

### Pitfall 4: Using Access `Bypass` As Anonymous Product Mode
**What goes wrong:** Anonymous entry becomes an infrastructure loophole instead of explicit Worker logic.
**Why it happens:** It looks simpler than implementing a mode flag.
**How to avoid:** Keep anonymous mode as an explicit Worker-owned runtime branch governed by one flag.

### Pitfall 5: Proxying To The Wrong Origin Host
**What goes wrong:** The Worker fetches the public hostname or another ambiguous host and creates loops or bypass confusion.
**Why it happens:** The public host and origin host are not modeled separately in config.
**How to avoid:** Use an explicit `ORIGIN_BASE_URL` or equivalent trusted origin setting that is distinct from the public answer hostname.

## Code Examples

### Recommended Worker Handler Shape
```ts
import { jwtVerify, createRemoteJWKSet } from "jose";

type Env = {
  ORIGIN_BASE_URL: string;
  ORIGIN_SHARED_SECRET: string;
  ENTRY_MODE: "authenticated-only" | "anonymous-enabled";
  WORKER_ALLOW_ANONYMOUS?: string;
  ACCESS_TEAM_DOMAIN?: string;
  ACCESS_POLICY_AUD?: string;
};

function allowAnonymous(env: Env): boolean {
  return env.ENTRY_MODE === "anonymous-enabled" && env.WORKER_ALLOW_ANONYMOUS === "true";
}

async function validateAccess(request: Request, env: Env): Promise<void> {
  if (env.ENTRY_MODE !== "authenticated-only") return;
  if (!env.ACCESS_TEAM_DOMAIN || !env.ACCESS_POLICY_AUD) {
    throw new Response("Missing Access config", { status: 403 });
  }

  const token = request.headers.get("cf-access-jwt-assertion");
  if (!token) throw new Response("Missing Access JWT", { status: 401 });

  const jwks = createRemoteJWKSet(new URL(`${env.ACCESS_TEAM_DOMAIN}/cdn-cgi/access/certs`));
  await jwtVerify(token, jwks, {
    issuer: env.ACCESS_TEAM_DOMAIN,
    audience: env.ACCESS_POLICY_AUD,
  });
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    if (env.ENTRY_MODE === "anonymous-enabled" && !allowAnonymous(env)) {
      return new Response("Anonymous disabled", { status: 403 });
    }

    await validateAccess(request, env);

    const target = new URL(request.url);
    const origin = new URL(env.ORIGIN_BASE_URL);
    target.protocol = origin.protocol;
    target.host = origin.host;

    const outbound = new Request(target.toString(), request);
    outbound.headers.set("x-worker-origin-auth", env.ORIGIN_SHARED_SECRET);

    return fetch(outbound);
  },
};
```

## State Of The Art

| Older assumption | Current guidance | Impact on 04.6 |
|------------------|------------------|----------------|
| Worker should own the public hostname as a Custom Domain even when proxying an existing origin | Routes are the more Cloudflare-native fit when Worker logic fronts an existing origin application | 04.6 should use a Route-based Worker in front of `apps/supervisor-api` |
| `workers.dev` is a fine default public endpoint | Production Workers should use routes or custom domains; `workers.dev` should be disabled when not intended | 04.6 must set `workers_dev = false` |
| Preview URLs are just a dev detail | Preview URLs are public when enabled and must be managed explicitly | 04.6 must set `preview_urls = false` unless later separately protected |
| Access in front of a Worker is enough by itself | Cloudflare says the Worker should still validate `Cf-Access-Jwt-Assertion` | 04.6 authenticated mode needs real JWT validation code |
| Worker tests can be plain Node request mocks | Cloudflare recommends the Workers Vitest integration | 04.6 should use Worker-runtime tests, not only Node-level stubs |

## Open Questions

1. Should the trusted origin remain Internet-routable but protected by shared secret/header only, or should later delivery also move it behind a stricter private-origin path?
Current recommendation for 04.6: do not reopen topology. Keep the current trusted-origin model and enforce fail-closed auth at the runtime seam.

2. Should `apps/supervisor-api` continue supporting direct bearer traffic once the Worker path exists?
Current recommendation for 04.6: keep any existing non-Worker path only if already required by current local/dev workflows; otherwise prefer closing direct public dependency over time. Do not let this question block the Worker implementation.

3. Should Worker-forwarded runtime-mode metadata be consumed by `apps/supervisor-api` now?
Current recommendation for 04.6: only if needed for transport/runtime observability. Do not freeze it as final actor or authorization semantics.

## Bottom Line

04.6 should not be planned as “just write a Worker.” It should be planned as one runtime seam implementation:

- a dedicated Worker app under `apps/*`
- explicit mode enforcement and JWT validation in the Worker
- explicit secret-backed Worker-to-origin trust
- a small companion auth/runtime patch in `apps/supervisor-api`
- focused Worker-runtime tests and API-shell trust tests

Anything beyond that, especially actor semantics, ACL, or audit closure, belongs to Phase 5 rather than 04.6.
