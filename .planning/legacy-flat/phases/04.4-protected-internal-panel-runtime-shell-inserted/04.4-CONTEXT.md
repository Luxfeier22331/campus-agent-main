# Phase 04.4: Protected Internal Panel Runtime Shell - Context

**Gathered:** 2026-03-25
**Status:** Ready for planning
**Source:** Derived from the inserted roadmap phase, Phase 04.1/04.2 outputs, and current planning/state constraints

<domain>
## Phase Boundary

Phase 04.4 freezes the implementation shape of the protected internal panel as a future `apps/` runtime shell.

The scope is to make explicit:

- where the panel lives in the repo shape
- what runtime API seam it may consume
- what fail-closed assumptions must remain true
- which non-goals and deferred areas still belong outside the panel runtime-shell phase

This phase does not design panel UI, panel business workflows, or app-layer auth/ACL/audit behavior.

</domain>

<decisions>
## Implementation Decisions

### Locked by roadmap and prior phases
- Protected panel remains a separate protected surface and future `apps/` runtime origin.
- Protected panel must consume runtime APIs only.
- Panel must not become `apps/supervisor-api` hidden admin mode.
- Delivery ownership and rollback seams from 04.2 must remain intact.
- Actor, ACL, and audit closure remain Phase 5 work.

### Locked phase intent for 04.4
- Freeze the repo/runtime shape of the protected panel.
- Freeze allowed runtime API seams and fail-closed expectations.
- Freeze panel non-goals so later work does not smuggle in workflow/business scope.

### Explicit non-goals
- Do not implement panel pages, routes, or UI.
- Do not define panel-side business operations.
- Do not define package-level imports or direct package coupling.
- Do not solve `SupervisorRequest.actor`, retrieval ACL, audit closure, or approval flow.

### The agent's Discretion
- Exact decomposition into one canonical runtime-shell note plus one planning handoff note, or a similarly small artifact set.
- Exact terminology for panel shell, runtime API seam, protected operator surface, and fail-closed delivery assumptions.

</decisions>
