## Summary

Phase 04.1 already froze who owns the edge boundary and protected panel trust model. Phase 04.2 should therefore freeze the next layer down: the runtime topology and delivery ownership between Cloudflare surfaces and repo-owned runtime origins.

The clean shape is:

- public entry hostname routes through Cloudflare to the `apps/supervisor-api` runtime origin
- protected panel hostname routes through Cloudflare-protected access to a separate future `apps/` runtime origin
- any shared substrate remains a hosting/deployment decision, not a reason to collapse the two runtime boundaries into one app or one package boundary

The topology freeze should explicitly name:

- hostname-to-origin mapping
- who owns secrets/config versus package config
- what the rollback unit is for each surface
- which delivery concerns are allowed in `apps/*` and which are forbidden from leaking into `packages/*`

**Primary recommendation:** treat 04.2 as a two-artifact doc/design phase: one canonical topology note under `docs/architecture/`, plus one concise delivery handoff note in `.planning/` that future 04.3/04.4 implementation planning can consume.

## Phase Boundary

### Cloudflare Owns

- public and protected hostname entry points
- TLS/DNS and edge-facing admission
- surface-to-origin routing at the edge
- upstream protection envelope for the protected panel surface

### Repo-Owned Runtime Owns

- runtime origins under `apps/*`
- runtime-specific environment/config loading
- transport-level request handling after the request reaches an origin
- runtime rollback and deploy-unit boundaries

### Core Packages Must Not Change For This Phase

- `packages/contracts`
- `packages/supervisor-core`
- `packages/rag-specialist`
- `packages/retrieval-core`
- `packages/ingestion-core`

## Topology Truths To Freeze

1. Public entry origin remains `apps/supervisor-api`; Cloudflare does not front a core package directly.
2. Protected panel remains a separate future `apps/` runtime origin, even if it eventually shares infrastructure with the public entry.
3. Secret/config ownership belongs to deployment/runtime boundaries, not package contracts.
4. Rollback must be defined by surface/origin boundary, so public entry and protected panel can evolve independently.
5. Environment or provider-specific delivery concerns must stop at `apps/*` and docs/planning artifacts, not leak into core package types.
