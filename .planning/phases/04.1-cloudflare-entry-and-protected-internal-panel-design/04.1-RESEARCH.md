# Phase 04.1: Cloudflare Entry And Protected Internal Panel Design - Research

**Researched:** 2026-03-25
**Domain:** Cloudflare-facing runtime boundary and protected internal panel design
**Confidence:** HIGH

## User Constraints

### Locked Decisions

- This phase runs in parallel to Phase 4 as a design track.
- Use Cloudflare for public entry and panel hosting/protection.
- Internal panel must be protected and non-public by default.
- Do not let this phase become a rewrite of `packages/contracts`, `packages/supervisor-core`, `packages/rag-specialist`, or retrieval/runtime internals.

### Claude's Discretion

- Decide what Cloudflare should own versus what stays in `apps/supervisor-api`.
- Decide how public entry, panel hosting, and protected internal panel should be split.
- Decide which artifacts should be frozen now so later implementation can move quickly without architectural debt.

### Deferred Ideas

- Do not solve Phase 5 identity propagation, retrieval ACL, or audit semantics here.
- Do not freeze a long-term HTTP/runtime framework choice beyond the existing phase-1 boundary.
- Do not introduce panel-side business workflows, admin actions, or new supervisor/specialist contracts in this phase.

## Summary

This phase should freeze an edge/runtime split, not add application behavior. The clean shape is: Cloudflare owns the public edge entry, hostname split, and panel protection envelope; `apps/supervisor-api` remains the only repo-owned serving shell for supervisor requests; core packages remain unchanged.

The internal panel should be treated as a separate future runtime/app boundary under `apps/`, not as an extension of `apps/supervisor-api` and not as logic inside `packages/*`. This phase should therefore produce design artifacts that define the boundary, trust assumptions, and future implementation seams, while explicitly deferring identity/ACL/audit semantics to Phase 5.

**Primary recommendation:** Freeze a two-hostname model now: one Cloudflare-fronted public entry for user traffic, one Cloudflare-protected internal panel boundary, both above the existing `apps/ -> packages/` split.

## Phase Boundary

### Cloudflare Owns

- Public edge entry, DNS/TLS, hostname split, and edge-facing request admission.
- Protection envelope for the internal panel so it is non-public by default.
- Runtime-facing deployment boundary in front of repo apps; not package-level orchestration.

### `apps/supervisor-api` Owns

- The repo's public API shell and request/response mapping into `SupervisorRequest`.
- Auth/trace/runtime-shell concerns already assigned to `apps/`.
- Calling `packages/supervisor-core` without absorbing routing, policy, or retrieval logic.

### Core Packages Must Not Change For This Phase

- `packages/contracts`
- `packages/supervisor-core`
- `packages/rag-specialist`
- `packages/retrieval-core`

### Internal Panel Split

- The panel is a separate runtime/app concern, not a supervisor-core concern.
- If a panel app is added later, it belongs under `apps/`, behind Cloudflare protection, and consumes runtime-facing APIs instead of importing core orchestration internals.
- The panel must not become a backdoor entry that bypasses the supervisor-facing request boundary.

## Locked Decisions For Planning

1. Cloudflare is the edge/control boundary; the monorepo remains responsible only for runtime shells and core packages.
2. `apps/supervisor-api` stays the entry shell for supervisor requests; this phase does not move orchestration up into Cloudflare or down into packages.
3. The internal panel is protected by default and must not share the same exposure model as the public entry.
4. This is a boundary/design freeze only; Phase 5 keeps ownership of identity propagation, retrieval ACL, and audit closure.

**Outputs:**

**Outputs:**
