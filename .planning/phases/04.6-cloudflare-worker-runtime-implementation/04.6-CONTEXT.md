# Phase 04.6: Cloudflare Worker Runtime Implementation - Context

**Gathered:** 2026-03-25
**Status:** Ready for research
**Source:** Derived from the inserted roadmap phase, completed 04.1-04.5 Cloudflare outputs, current `apps/supervisor-api` auth/runtime behavior, and current planning/state constraints

<domain>
## Phase Boundary

Phase 04.6 implements the Cloudflare Worker public-entry runtime shell that was frozen by 04.3 and 04.5.

The scope is to make real runtime code exist for:

- the public Worker entry that fronts the public answer hostname
- Worker-side entry-mode enforcement for `authenticated-only` and `anonymous-enabled`
- Worker-side forwarding from a Route-hit public hostname to the trusted `apps/supervisor-api` origin
- Worker-to-origin trust projection and origin-side fail-closed enforcement
- Worker-local config, secrets, and focused runtime tests

This phase is not a Phase 5 replacement. It exists to implement the already-frozen Worker/runtime seam without pushing Cloudflare/provider semantics into `packages/*` and without claiming app-layer actor/ACL/audit closure.

</domain>

<decisions>
## Implementation Decisions

### Locked by roadmap and prior phases
- Cloudflare remains the public entry boundary in front of `apps/supervisor-api`, not an edge orchestrator.
- The public answer path stays `client -> public hostname -> Cloudflare Route -> Cloudflare Worker -> trusted origin/apps/supervisor-api -> packages/supervisor-core -> specialist`.
- `apps/*` remain runtime/transport boundaries; `packages/*` remain stable capability boundaries.
- Request-id / trace propagation stays separate from app-layer actor identity.
- Protected internal panel remains a separate protected surface and must not be merged into the public Worker runtime.
- `packages/contracts`, `packages/supervisor-core`, `packages/rag-specialist`, and retrieval/data-plane packages must not absorb Cloudflare/provider-specific types or entry policy semantics.

### Locked phase intent for 04.6
- Implement one Worker runtime shell under `apps/*`, not inside `packages/*`.
- Implement exactly the two frozen entry modes:
  - `authenticated-only`
  - `anonymous-enabled`
- Implement explicit Worker-to-origin trust using secret-backed runtime material such as `X-Worker-Origin-Auth`.
- Keep `workers_dev = false` and `preview_urls = false` as deployment/runtime invariants.
- Add only the minimal origin-side runtime/auth-shell changes required for the Worker path to run end-to-end.

### Explicit non-goals
- Do not implement final end-user auth architecture.
- Do not define or freeze `SupervisorRequest.actor`.
- Do not implement retrieval ACL or audit closure.
- Do not redesign supervisor-core routing, contracts, or package boundaries.
- Do not merge panel/operator behavior into the public Worker.

### Agent discretion
- Exact `apps/*` directory name for the Worker runtime shell.
- Exact Worker config file set, test layout, and local developer commands.
- Exact secret/env var names, as long as the seam remains runtime-scoped and fail-closed.
- Exact origin-auth enforcement shape inside `apps/supervisor-api`, as long as it remains transport/auth/runtime logic and does not leak into `packages/*`.

</decisions>

<specifics>
## Specific Ideas

- Treat 04.6 as a runtime implementation phase, not a new architecture discussion phase.
- Prefer a new Worker app under `apps/*`, analogous to `apps/ingestion-worker` as a runtime shell.
- Expect a small companion change in `apps/supervisor-api` auth/runtime code so origin requests can fail-closed on missing/invalid Worker trust material.
- Keep Worker-side behavior explicit:
  - mode selection
  - JWT validation when required
  - header allowlisting / forwarding
  - origin target selection
  - fail-closed rejection behavior
- Keep origin-side behavior explicit:
  - trusted Worker-origin auth acceptance
  - reject direct/malformed requests
  - no claim that Worker headers complete Phase 5 actor semantics

</specifics>
