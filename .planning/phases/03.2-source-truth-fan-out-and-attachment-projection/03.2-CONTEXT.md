# Phase 03.2: Source Truth Fan-Out And Attachment Projection - Context

**Gathered:** 2026-03-26
**Status:** Historical pre-execution context; Phase 03.2 implementation completed on 2026-03-26
**Source:** Derived from the inserted roadmap phase, phase-1 ingestion architecture docs, current ingestion-core / worker code, and the verified `student_handbook` chunk-truth baseline

<domain>
## Phase Boundary

Phase 03.2 closes a data-plane design gap that remained after Phase 2 and Phase 3 were implemented successfully for `student_handbook`.

At planning time, the repo already had a stable handbook raw-first path and stable handbook chunk/index truth, but downstream collection expansion still behaved as separate consumption lanes:

- `student_handbook` uses canonical raw-first ingestion and handbook replay.
- `campus_services` handbook-derived outputs had not yet converged onto the same source-truth projection contract.
- handbook attachments and navigation-like leaves can influence cleanup/chunking semantics, but they are not yet modeled as first-class derived documents.

This phase exists to freeze and then execute one stronger invariant:

- one raw source is consumed once
- one canonical source-truth layer is persisted once
- all declared downstream projections fan out from that source truth in the same architecture
- replay/rebuild reuses source truth rather than returning to raw

The scope is architecture and implementation planning for ingestion/data-plane convergence. The phase does not reopen chunking quality for `student_handbook`, does not expand query-serving scope, and does not redesign supervisor/retrieval package boundaries.

</domain>

<decisions>
## Implementation Decisions

### Locked by previous phases and current validation
- `student_handbook` chunk-truth is now considered stable enough to stop churn on cleanup/chunking as the mainline blocker.
- Raw assets remain the top-level provenance truth and are intentionally not organized by `corpus`, because one raw asset may feed multiple corpora or collections.
- `layout-elements.jsonl` remains the only asset-level internal structured truth between provider response and document-level derivation for handbook OCR ingestion.
- `document-units.jsonl` stays the direct chunking input for `student_handbook`; this phase does not redesign handbook chunk policy.
- `Qdrant` remains the canonical online chunk/index store; any new projection or source-truth artifact must not move online truth back into object-storage-only manifests.

### Phase 03.2 design intent
- Replace the current “one collection, one ingestion lane” drift with “single source consumption + multi-projection fan-out”.
- Treat source-truth persistence as the reusable rebuild boundary. Replaying a new collection from the same source should not require re-consuming raw PDF/OCR input if canonical source truth already exists.
- Make handbook attachments first-class derived documents when they have standalone downstream value, rather than leaving them only as cleanup-time semantics inside handbook text.
- Unify handbook-derived `campus_services` outputs with the same ingestion contract instead of maintaining a separate migration-only architecture line.
- Keep projection declaration repo-tracked and explicit. The repo should know, for one source asset, which downstream document families must be emitted.

### Problems this phase explicitly addressed
- `packages/ingestion-core/src/campus_ingestion_core/raw_ingestion.py` was still behaving as a handbook-oriented collection consumer rather than a source fan-out orchestrator.
- `packages/ingestion-core/src/campus_ingestion_core/local_rebuild.py` was still replaying from handbook source truth without yet rebuilding all declared downstream projections from that same source.
- Handbook-derived `campus_services` outputs were still maintained through a bridge path instead of through the same source-truth projection contract.
- `packages/ingestion-core/src/campus_ingestion_core/handbook_cleanup.py` already distinguished appendix/form/navigation-like content semantically, but those semantics had not yet been elevated into explicit derived-document outputs.

### Explicit non-goals
- Do not reopen tokenizer choice, handbook chunk policy, or sample-based chunk validation as the primary task of this phase.
- Do not expose `campus_services` to query-serving.
- Do not turn projection logic into retrieval-time logic or supervisor-side glue.
- Do not add one-off compatibility layers that preserve the current split forever. The goal is to converge onto one ingestion contract, not to document permanent dual paths.

### the agent's Discretion
- Exact config filename and schema shape for source-truth projection declarations, as long as it is repo-tracked and collection-agnostic.
- Exact decomposition between source-truth projection planning and worker/replay convergence planning, as long as architecture freeze lands before execution details.
- Exact naming for attachment kinds and parent/derived metadata fields, as long as parent/source provenance and replayability are explicit.

</decisions>

<code_context>
## Existing Code Insights

### What is already working
- Handbook raw-first ingestion already produces source-level and document-level processed artifacts from registered raw assets.
- Handbook replay can rebuild processed artifacts and optionally refresh index state from persisted `provider-response.jsonl`.
- Handbook chunk validation now exports real samples and verifies the stabilized cleanup/chunking path against the live registry/object store.

### Historical architecture split before implementation
- `raw_ingestion.py` was still collection-shaped. It knew how to build handbook documents, but not how to declare or orchestrate multiple downstream projections from one source-truth run.
- `local_rebuild.py` already understood replay from persisted provider response, but it had not yet been extended to rebuild all declared downstream outputs from that same source-truth run.
- Handbook-derived `campus_services` outputs were still emitted through a bridge contract rooted in legacy canonical files rather than the same repo-tracked projection contract.
- handbook cleanup already classified appendix-like and navigation-like content well enough for chunking, which meant attachment projection should be built on top of existing document/source truth rather than on new OCR heuristics.

### Required convergence points
- source-truth persistence must become an explicit artifact boundary that later projections can consume without raw re-entry
- projection declaration must move from ad hoc code/config pairing into one canonical repo-tracked contract
- handbook-derived service documents and future attachments/forms/navigation leaves must share identity/provenance conventions with handbook ingestion
- replay/rebuild must dispatch by declared projections and source truth, not by handbook-specific branching alone

</code_context>

<specifics>
## Specific Ideas

- The likely architecture shape is:
  - `raw asset -> provider-response.jsonl -> layout-elements.jsonl -> source truth -> declared projections -> document artifacts -> chunks/index`
- A dedicated projection config under `configs/ingestion/regulations/student_handbook/` is likely needed, for example `source-projections.v1.json`.
- Derived document metadata likely needs explicit linkage such as:
  - `projection_name`
  - `derived_from_raw_asset_id`
  - `derived_from_raw_version_id`
  - `derived_from_document_id`
  - `parent_document_id`
  - `attachment_kind`
- Attachment kinds should stay semantic and retrieval-oriented, not PDF-layout-oriented. Current likely families are:
  - `narrative_appendix`
  - `tabular_appendix`
  - `form_template`
  - `navigation_like`

</specifics>
