# Phase 04.5: Cloudflare Worker Consumer Entry And Access Policy - Context

**Gathered:** 2026-03-25
**Status:** Ready for planning
**Source:** Derived from the inserted roadmap phase, completed 04.1-04.4 Cloudflare outputs, current API-shell auth behavior, and current planning/state constraints

<domain>
## Phase Boundary

Phase 04.5 freezes the consumer-facing Cloudflare Worker entry shape and access policy for the public answer path.

The scope is to make explicit:

- how a Cloudflare Worker serves as the only public consumer-entry shell
- whether anonymous usage is allowed and how a flag controls that behavior
- what minimum login-vs-anonymous access policy belongs at the Worker/origin seam
- how Worker-to-origin trust, identity projection, and fail-closed behavior remain runtime concerns
- which auth, actor, ACL, and audit concerns remain deferred outside this phase

This phase is not a Phase 5 replacement. It exists to define the minimum Worker consumer-entry and access-policy contract needed to implement a real public entry without pushing auth/provider semantics into `packages/*`.

</domain>

<decisions>
## Implementation Decisions

### Locked by roadmap and prior phases
- Public entry remains `client -> Cloudflare public entry -> apps/supervisor-api -> packages/supervisor-core -> specialist`.
- Cloudflare public entry stays an edge/runtime concern, not an edge orchestrator.
- `apps/supervisor-api` remains the only public runtime ingress and continues to own transport/auth/runtime mapping before supervisor-core.
- request-id / trace propagation stays separate from app-layer actor identity.
- protected internal panel remains a separate protected surface and must not be merged into public entry behavior.
- `packages/contracts`, `packages/supervisor-core`, `packages/rag-specialist`, and retrieval/data-plane packages must not absorb Cloudflare/provider-specific types or entry policy semantics.

### Locked phase intent for 04.5
- Freeze a canonical architecture note for Cloudflare Worker as the public consumer-entry shell.
- Freeze an entry-level access policy that supports both authenticated-only mode and optional anonymous mode behind an explicit flag.
- Freeze the minimum Worker-to-origin trust contract so the origin is not treated as directly public.
- Freeze what is intentionally still deferred to Phase 5 and later governance work.

### Explicit non-goals
- Do not implement Phase 5 actor mapping, retrieval ACL, or audit closure.
- Do not introduce a new specialist, worker-runtime, or panel workflow.
- Do not redesign supervisor-core routing, contracts, or package boundaries.
- Do not require final end-user auth provider selection or final identity system freeze.
- Do not turn public entry into a hidden panel/admin surface.

### the agent's Discretion
- Exact decomposition into one canonical access-policy architecture note plus one implementation handoff/checklist, or a similarly small artifact set.
- Exact naming of the anonymous-access flag, trusted identity headers, Worker-to-origin secret/header, and fail-closed entry posture, as long as they remain runtime-boundary concerns.
- Whether the plan should also update docs index or roadmap wording for discoverability.

</decisions>

<specifics>
## Specific Ideas

- Treat 04.5 as a consumer-entry/access-policy phase, not as a general runtime phase.
- The Worker should become the only public hostname entry and forward only to `apps/supervisor-api`.
- The access-policy note should distinguish two modes:
  - authenticated users only
  - anonymous allowed behind an explicit flag
- The phase should define minimum Worker-to-origin trust so origin access remains protected even if the Worker is the public consumer entry.
- The phase should keep Cloudflare entry access policy separate from Phase 5 app-layer actor/ACL/audit semantics.

</specifics>
