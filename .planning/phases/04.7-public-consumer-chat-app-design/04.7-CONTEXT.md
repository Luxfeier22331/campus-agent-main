# Phase 04.7: Public Consumer Chat App Design - Context

**Gathered:** 2026-03-26
**Status:** Ready for planning
**Source:** Derived from the inserted roadmap phase, completed 04.1-04.6 public-entry outputs, the new public consumer chat surface architecture note, and current project constraints

<domain>
## Phase Boundary

Phase 04.7 defines the first-version product and implementation shape for a consumer-facing chat app that sits on top of the already-frozen public-entry Worker path.

The scope is to make explicit:

- what the v1 consumer chat product includes and excludes
- how the app lives under `apps/*` without collapsing into `apps/public-entry-worker` or `apps/supervisor-api`
- what minimum app-level user/session and conversation ownership is required
- what chatbox, sidebar, routing, and required UX states belong in the MVP
- which seams remain deferred to Phase 5 actor/ACL/audit closure

This phase is not a panel phase, not a runtime-unification phase, and not a replacement for Phase 5 identity/ACL work. It exists to define and plan the public user-facing chat surface so implementation can proceed without reopening Cloudflare or package-boundary questions.

</domain>

<decisions>
## Implementation Decisions

### Locked by roadmap and prior phases
- Public entry remains `public hostname -> Cloudflare Route -> Cloudflare Worker -> apps/supervisor-api -> packages/supervisor-core -> specialist`.
- Cloudflare Worker remains the only public ingress shell and does not become an edge orchestrator.
- `apps/supervisor-api` remains the only public runtime ingress and continues to own transport/runtime mapping before supervisor-core.
- protected internal panel remains a separate protected surface and must not be mixed into this app.
- `packages/*` must not absorb frontend framework, auth provider, Cloudflare, or conversation-UI concerns.

### Locked phase intent for 04.7
- Define a chat-first public consumer app with sidebar conversation history, a primary chatbox, and app-level user session UX.
- Keep the consumer app under `apps/*` as a separate app boundary from both `apps/public-entry-worker` and `apps/supervisor-api`.
- Treat app auth/session and conversation ownership as product/runtime concerns, while explicitly not claiming final `SupervisorRequest.actor`, retrieval ACL, or audit closure.
- Break the work into implementation-ready tasks covering app shell, auth/session integration, conversation model, chat interaction, and runtime API seam.
- Plan the first product MVP as authenticated-first once conversation history and ownership are required.
- Freeze the v1 browser-to-answer transport assumption rather than leaving same-site versus cross-origin routing to later implementation drift.

### Explicit non-goals
- Do not design or implement panel/admin/operator workflow.
- Do not move canonical user-system truth or retrieval ACL ownership into the Worker.
- Do not expose specialist/runtime/provider concepts in the product surface.
- Do not freeze final frontend framework, database, or auth provider as long-term architecture truth beyond this app line.
- Do not claim Phase 5 actor/group propagation, retrieval ACL filtering, or audit closure is complete.
- Do not add attachments, tools workspace, shared conversations, or multi-surface admin affordances to v1.

### the agent's Discretion
- Exact decomposition of the phase into design-only and implementation plans.
- Whether the first implementation pass should scaffold the app shell before full chat wiring, as long as the product boundary stays intact.
- Exact naming of the future app directory, frontend stack, and user/session persistence approach, as long as it remains in `apps/*`, respects the Worker/origin seam, and supports self-maintained app auth.

</decisions>

<specifics>
## Specific Ideas

- v1 should look like a lightweight ChatGPT/Claude-style consumer chat product:
  - sidebar conversation history
  - primary chatbox
  - top bar with current user and new chat
- minimum routes should be `/login`, `/chat`, and `/chat/:conversationId`
- required states include `login`, `empty`, `answer`, `clarification`, `error`, and `history`
- the consumer app should own app-level session UX and conversation ownership UX
- the Worker should continue to own outer admission, not canonical app identity or ACL truth
- the first implementation path should likely separate:
  - app shell and routes
  - auth/session integration
  - conversation persistence
  - chat transport and rendering

</specifics>

<deferred>
## Deferred Ideas

- final actor/group propagation into supervisor request contracts
- retrieval ACL closure
- audit/trace governance closure
- panel-side product design
- multi-tool workspace
- attachments and uploads
- shared conversations, organizations, and fine-grained role behavior

</deferred>
