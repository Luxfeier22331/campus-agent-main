## Summary

The repo-local architecture is already decisive on the most important planning question: this phase is not deciding whether a public chat product exists, but how to model it without breaking the 04.1-04.6 Cloudflare and runtime freezes. The public chat surface must be a separate `apps/*` consumer-facing app, must stay chat-first, and must keep answer execution on the existing `public hostname -> Worker -> apps/supervisor-api -> supervisor-core` path. The app is allowed to own UI, routes, session UX, and conversation ownership. It is not allowed to absorb Worker admission, supervisor routing, package contracts, or Phase 5 actor/ACL/audit semantics.

The cleanest implementation shape for that boundary is a dedicated full-stack frontend app under `apps/public-consumer-chat` using React Router framework mode, React 19, Better Auth, and TanStack Query. That stack keeps UI routes, server-side auth/session endpoints, and conversation CRUD inside one app boundary without forcing those concerns into `apps/supervisor-api` or `packages/*`. Better Auth now has first-party React Router integration, and React Router’s current framework tooling gives a lightweight server/client app shape without turning the whole monorepo into a Next.js-style runtime commitment. This is a phase recommendation for the app line, not a repo-wide architecture freeze.

The main planning trap is identity confusion. The Worker may keep deciding whether a request can reach the public answer path, but app-level identity truth still belongs to the consumer app, and final actor/group/ACL/audit truth still belongs to Phase 5. The plan should therefore treat 04.7 as authenticated-first by default for the actual product MVP. That is an inference from the local docs: once conversation history and ownership are required, `anonymous-enabled` remains a Worker capability but is a poor default product mode for v1.

**Primary recommendation:** Plan 04.7 as a separate `apps/public-consumer-chat` boundary, freeze authenticated-first app session plus conversation ownership at the app layer, keep answer transport on the existing Worker/runtime seam, and split the phase so design truth lands before full auth/database wiring.

### Pattern 1: Dedicated Consumer App Boundary
**What:** Model the product as a new `apps/*` app, not as a mode of `public-entry-worker` and not as server-rendered pages inside `apps/supervisor-api`.
**When to use:** Always for public consumer chat implementation.
**Example:**
```text
Allowed:
- apps/public-consumer-chat owns login route, top bar, sidebar, session UX, conversation list, and message rendering

Forbidden:
- apps/public-entry-worker serves as the UI shell
- apps/supervisor-api grows template/page ownership
- packages/* receives frontend, auth-provider, or chat UI code
```

### Pattern 2: Three-Layer Identity Split
**What:** Keep Worker admission, app session identity, and Phase 5 actor/ACL truth as three separate layers.
**When to use:** Always; this is the core boundary that prevents design drift.
**Example:**
```text
Layer 1: Worker/runtime admission
- decides whether the public answer path is reachable
- carries trace/runtime metadata only

Layer 2: consumer app identity
- owns login state
- owns session cookie/token
- owns conversation ownership and "my history"

Layer 3: Phase 5 governance
- final SupervisorRequest.actor mapping
- retrieval ACL
- audit closure
```

### Pattern 3: Conversation Ownership Lives At The App Layer
**What:** Keep durable `user -> conversation -> message` ownership inside the consumer app’s persistence boundary.
**When to use:** Always once sidebar history is part of v1.
**Example:**
```ts
type AppConversation = {
  id: string;
  ownerUserId: string;
  title: string;
  createdAt: string;
  updatedAt: string;
};

type AppMessage = {
  id: string;
  conversationId: string;
  role: "user" | "assistant";
  text: string;
  traceId?: string;
};
```

### Pattern 4: Chat Transport Is A Runtime API Seam, Not A Shared Contract Rewrite
**What:** The app sends chat prompts to the existing answer path and maps the resulting status into product states. It does not import `packages/contracts` or invent new supervisor-facing semantics in the browser.
**When to use:** Always for ask/answer execution.
**Example:**
```ts
type SendMessageRequest = {
  conversationId: string;
  userGoal: string;
};

type ChatUiResult =
  | { kind: "answer"; text: string; traceId: string; citations?: unknown[] }
  | { kind: "clarification"; text: string; traceId: string }
  | { kind: "error"; message: string; traceId?: string };
```

### Pattern 5: Request/Response First, Streaming Later
**What:** Treat streaming as an explicit later runtime capability, not as a prerequisite for the first app shell.
**When to use:** First implementation wave.
**Example:**
```text
Wave 1 UI states:
- input idle
- sending
- answer
- clarification
- error

Deferred:
- token streaming
- partial assistant chunks
- resumable stream reconnect
```

### Pattern 6: Split Design Freeze From Full Product Wiring
**What:** Land boundary truth, route/state truth, and implementation slices before committing to the full auth/database/chat build.
**When to use:** This phase.
**Example:**
```text
Design-only first:
1. app boundary + directory contract
2. route/state contract
3. identity/ownership matrix
4. answer API seam contract

Implementation after:
1. shell scaffold
2. auth/session integration
3. conversation persistence
4. chat transport wiring
```

### Anti-Patterns to Avoid
- **Worker-as-UI host:** `apps/public-entry-worker` must not become a chat frontend runtime just because it already owns the public hostname seam.
- **App user equals `SupervisorRequest.actor`:** 04.7 must not freeze browser/app identity as Phase 5 actor truth.
- **Conversation ownership enforced only in the client:** history filtering and conversation lookup must be server-side.
- **Anonymous-first MVP with durable history:** this fights the local product shape and makes ownership rules much harder before Phase 5.
- **Streaming-first scope:** the runtime seam already treats streaming as a separate concern; making it mandatory will distort the phase.
- **Direct `packages/*` imports from the app:** the consumer app consumes runtime APIs only.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| App auth/session | Custom cookie/session/auth flows | Better Auth | Login, session rotation, account flows, and adapters are easy to get subtly wrong |
| Chat server-state | Local reducer plus ad hoc fetch invalidation | TanStack Query | Conversations, messages, retries, mutation state, and invalidation are standard server-state problems |
| Route pending/error plumbing | Manual route-state coordination everywhere | React Router loaders/actions/fetchers | Route-level pending/error handling is built into the framework model |
| Cross-user ownership checks | Client-side `userId === ownerId` only | Server-side conversation ownership guard in the app boundary | Sidebar history and `/chat/:conversationId` require real access control |
| Session storage with no database | Stateless session-only auth for a history product | Database-backed auth/session plus conversation tables | Better Auth’s docs note stateless mode is limited and most real plugins/features need a database anyway |

**Key insight:** the tricky work in this phase is not the chat textbox. It is making user session, conversation ownership, and answer transport explicit without reopening Worker admission or Phase 5 governance.

## Common Pitfalls

### Pitfall 1: Treating Worker Admission As Canonical User Identity
**What goes wrong:** The plan assumes Cloudflare Access or Worker headers are enough to define app user identity.
**Why it happens:** The public answer path already has a real Worker seam, so it is tempting to reuse that as the product auth system.
**How to avoid:** Keep Worker admission as entry policy only. The consumer app owns app session UX and conversation ownership. Phase 5 still owns final actor/ACL/audit semantics.
**Warning signs:** Planning language says the app “just uses the Worker identity” without defining app session storage or ownership rules.

### Pitfall 2: Picking Stateless Auth For A History Product
**What goes wrong:** Login exists, but durable history/ownership still needs separate storage, causing a second identity system later.
**Why it happens:** Stateless auth sounds simpler at first.
**How to avoid:** Treat database-backed auth and conversation persistence as the same app-layer boundary.
**Warning signs:** The plan says “session only” but also promises sidebar history and owned threads.

### Pitfall 3: Cross-Origin Chat API Without A CORS Decision
**What goes wrong:** Browser calls from the app host to the Worker answer host fail or become operationally messy in authenticated-only mode.
**Why it happens:** The current docs freeze the answer seam, but not the final public app delivery topology.
**How to avoid:** Prefer same-site path routing for answer calls if possible; if not, make Cloudflare Access CORS and cookie behavior an explicit plan dependency.
**Warning signs:** The plan assumes the browser can call the answer Worker from another origin “later.”

### Pitfall 4: Requiring Final Phase 4/5 Semantics Before Building The Shell
**What goes wrong:** The app plan blocks on citations, final clarification wording, or final actor propagation.
**Why it happens:** The product surface wants those features eventually.
**How to avoid:** Design the UI states now, but let citations be optional and keep actor/ACL/audit explicitly deferred.
**Warning signs:** The plan cannot start until QRY-02 or GOV-01/GOV-02 are fully complete.

### Pitfall 5: Letting The App Turn Into A Panel
**What goes wrong:** Scope creeps into admin routes, workspace affordances, attachments, or model/specialist selectors.
**Why it happens:** Chat apps naturally invite “one more tool surface.”
**How to avoid:** Enforce the frozen v1 IA: `/login`, `/chat`, `/chat/:conversationId`, plus sidebar, chat panel, and top bar only.
**Warning signs:** New route proposals include settings, admin, workspace, docs, or source management.

### Pitfall 6: Forgetting Monorepo Tooling Reality
**What goes wrong:** The plan assumes a root JS workspace already exists.
**Why it happens:** There is already one TypeScript app in `apps/public-entry-worker`.
**How to avoid:** Treat the new app as another isolated app-local Node project first, just like `apps/public-entry-worker`.
**Warning signs:** The plan starts by introducing a repo-wide JS toolchain migration that is unrelated to the phase goal.

## Open Questions

1. **Will the consumer app and answer API be same-site or cross-origin?**
   - What we know: The Worker/public answer seam is frozen, but the final public app delivery shape is not.
   - What's unclear: Whether browser chat calls will hit the Worker on the same hostname/path or a different origin.
   - Recommendation: Treat this as a required planning decision because authenticated-only mode gets materially harder cross-origin.

2. **Which database/runtime store will own auth plus conversations?**
   - What we know: The app needs durable users, sessions, and conversation ownership; final database choice is intentionally not frozen long-term.
   - What's unclear: SQLite-for-first-pass vs Postgres-compatible from day one.
   - Recommendation: Keep the model relational and app-owned in 04.7; choose the smallest database that Better Auth and conversation ownership can share without inventing a second identity store.

3. **Is anonymous product mode actually part of the first user-facing MVP?**
   - What we know: 04.5/04.6 support `anonymous-enabled` at the Worker boundary, while 04.7 freezes login/session/history as product states.
   - What's unclear: Whether product wants anonymous users despite durable history and ownership requirements.
   - Recommendation: Plan v1 as authenticated-only and keep anonymous mode as a deferred or explicit follow-up product decision.

4. **Should the first implementation wave stop at shell + contracts, or include real auth and persistence?**
   - What we know: The context explicitly leaves this decomposition to agent discretion.
   - What's unclear: Whether the repo wants a pure design freeze first or a scaffolded app immediately after.
   - Recommendation: Split it. Freeze boundary/IA/ownership/API truth first, then implement shell/auth/persistence/chat in separate plans.
