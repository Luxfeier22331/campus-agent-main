## User Constraints (from CONTEXT.md)

### Locked Decisions

### Why this phase is current scope
- The current milestone still centers the `student_handbook` mainline, but a stable non-RAG specialist is now accepted as a parallel inserted phase because it validates the long-term specialist architecture on a second capability boundary.
- This phase must stay explicit in roadmap and requirements; it must not be hidden inside Phase 4 or Phase 5 and must not be described as a temporary verification hack.

### Routing posture
- `supervisor` remains the only coordinator and routes to availability through an explicit target or request kind, not through free-form intent classification.
- The first iteration should use an explicit route hint or typed request branch rather than model-based intent inference.
- Do not overload `KnowledgeScope.collection` or corpus fields to encode availability checks.
- Do not inline generic web tools into `supervisor-core`.

### Contract posture
- `packages/contracts` must stop assuming `DelegateToRagAgentRequest` / `DelegateToRagAgentResponse` are the only delegation shapes.
- The first refactor may use a discriminated union or a shared envelope with specialist-specific payloads, but it must remain typed; no unstructured dict blob or runtime-native payload is acceptable.
- Availability needs its own typed request/response payload or equivalent discriminated branch; retrieval-centric `EvidenceBundle` alone is not sufficient.
- Shared terminal status semantics may stay aligned with the current `completed` / `needs_clarification` / `no_answer` / `error` model if they remain meaningful for both specialist families.

### Availability target and probe policy
- The first iteration is restricted to allowlisted official-web targets defined in repo config or code, not arbitrary user-supplied URLs.
- Probe truth should be HTTP(S)-level reachability, redirect, timeout, and failure classification; raw ICMP `ping` is not the canonical contract because many official sites block it.
- Lower-level checks may exist behind the specialist for diagnostics, but the public contract should expose site observation semantics rather than shell/network primitives.
- The first output should at least capture target identity, observed status, HTTP status or redirect outcome when available, final URL when followed, and failure classification when unreachable.

### Terminal semantics
- A down site, timeout, DNS failure, TLS failure, or non-expected HTTP result from an allowlisted target is normally a successful observation and should return `completed`, not a specialist execution `error`.
- Only unsupported target, invalid route/request shape, missing allowlist configuration, or internal probe execution failure should return `error`.
- This phase does not need `needs_clarification` unless the request shape itself lacks target identity and the chosen contract still allows an incomplete availability request.

### Package boundary
- Create a real `packages/availability-specialist` package rather than extending `rag-specialist`.
- `packages/supervisor-core` owns route evaluation and final response assembly only.
- `packages/retrieval-core`, `packages/ingestion-core`, and handbook corpus semantics remain unchanged.
- If a later runtime uses tools to execute probes, those tools stay behind the specialist boundary rather than becoming supervisor-level shared tools.

### Claude's Discretion
- Whether the typed supervisor-to-specialist handoff uses one shared envelope plus specialist-specific payloads or parallel request/response pairs, as long as the contract remains explicit and typed.
- Whether the first availability response returns a short human-readable answer plus a structured observation block, as long as final status semantics stay machine-checkable.
- Whether verification begins with focused unit/integration tests or adds a tiny smoke runner immediately, as long as the phase yields repeatable proof of the availability path.

### Deferred Ideas (OUT OF SCOPE)
- Arbitrary URL inspection or open-web browsing beyond an allowlisted official target set
- Broad multi-specialist orchestration matrices or supervisor-level workflow engines
- Model-based intent classification to choose the availability path
- Supervisor-level shared browser or probe tool bundles
- Production-grade monitoring, scheduled probes, or incident-management semantics
- Using the availability specialist as a substitute for handbook chunk-truth closure

## Summary

This phase does not need a new orchestration runtime or a browser stack. The repo already has the right long-term architecture for a second specialist: `supervisor` stays the only coordinator, `packages/contracts` remains runtime-neutral, and the new capability lands as a real package instead of a tool bundle or a `rag-specialist` sidecar.

The missing piece is not “how to hit a URL.” The missing piece is how to generalize the current rag-only contract and single-delegate supervisor flow without reopening retrieval boundaries. The cleanest minimal shape is a typed common envelope for shared fields (`request_id`, `trace`, `actor`, `conversation_id`, `user_goal`) plus specialist-specific request/response payload dataclasses. That keeps routing explicit, preserves the existing supervisor pipeline, and avoids leaking retrieval-only fields into availability work.

For the actual probe, use `httpx.Client` inside `packages/availability-specialist`. Official HTTPX docs already cover the exact primitives this phase needs: client reuse, explicit redirect policy, default and tuned timeouts, transport-level mocking, and exception families. The contract should treat HTTP responses, redirects, timeouts, and transport failures as observations; only unsupported targets, bad request shape, missing allowlist config, or internal execution faults should become `error`.

**Primary recommendation:** Generalize the handoff into a typed common envelope, add `packages/availability-specialist` backed by `httpx.Client`, and map all site-state outcomes to structured `completed` observations while keeping `error` reserved for request/config/execution faults.

## Architecture Patterns

### Pattern 1: Shared Envelope With Specialist-Specific Payloads
**What:** keep one typed top-level envelope for common supervisor fields, then carry a specialist-specific payload/result branch under an explicit discriminant such as `request_kind` or `target`.

**When to use:** all supervisor-to-specialist calls, including the existing RAG path and the new availability path.

**Example:**
```python
from dataclasses import dataclass, field
from typing import Literal

SpecialistTarget = Literal["rag-specialist", "availability-specialist"]

@dataclass(frozen=True, slots=True)
class AvailabilityCheckPayload:
    target_id: str
    follow_redirects: bool = True

@dataclass(frozen=True, slots=True)
class SpecialistRequest:
    target: SpecialistTarget
    user_goal: str
    conversation_id: str = "bootstrap-conversation"
    request_id: str = ""
    trace: TraceContext = field(default_factory=TraceContext)
    actor: ActorContext = field(default_factory=ActorContext)
    payload: object = field(default_factory=AvailabilityCheckPayload)
```
Source: repo architecture and contract direction from `docs/architecture/long-term-architecture.md`, `docs/architecture/supervisor-architecture.md`, and `packages/contracts/src/campus_contracts/models.py`.

### Pattern 2: Explicit Supervisor Dispatch Table
**What:** routing returns an explicit specialist target, then `supervisor-core` dispatches through a target-to-delegate map. Do not keep the current `if target != "rag-specialist": raise ...` shape.

**When to use:** whenever `supervisor-core` handles more than one stable specialist boundary.

**Example:**
```python
delegate = delegates[decision.target]
specialist_response = delegate(context.request)
finalized_response = finalize_specialist_response(specialist_response)
return assemble_response(finalized_response)
```
Source: current pipeline in `packages/supervisor-core/src/campus_supervisor_core/agent.py`; this pattern preserves the existing `context -> routing -> delegation -> policy -> response assembly` flow while generalizing dispatch.

### Pattern 3: Availability Specialist Owns Probe Policy
**What:** the new package should contain three package-local pieces: allowlist resolution, HTTP probe execution, and mapping from raw HTTPX outcomes to typed observation results.

**When to use:** all availability requests in this phase.

**Example:**
```python
def check_target(request: AvailabilityCheckPayload, client: httpx.Client) -> AvailabilityResult:
    target = resolve_allowlisted_target(request.target_id)
    observation = probe_target(target, client)
    return map_observation_to_result(target, observation)
```
Source: repo boundary rules in `docs/architecture/long-term-architecture.md`, `docs/architecture/supervisor-architecture.md`, and Phase 03.1 context.

### Pattern 4: Observation Semantics Separate From Execution Faults
**What:** distinguish “the site is down / timed out / redirected / returned 503” from “the specialist itself could not execute because the request or config was invalid.”

**When to use:** every availability response.

**Example:**
```python
if observation.status in {"ok", "redirected", "http_error", "timeout", "connect_failure", "tls_failure"}:
    return SpecialistResponse(status="completed", result=observation)

return SpecialistResponse(
    status="error",
    error=ErrorInfo(code="availability_probe_failed", message="missing allowlist entry"),
)
```
Source: Phase 03.1 context terminal-semantics rules + current supervisor policy model.

### Anti-Patterns to Avoid
- **Overloading `KnowledgeScope`:** availability is not a fake corpus or collection; adding it there would re-couple supervisor routing to retrieval semantics.
- **Supervisor-owned probing:** do not inject `httpx`, `curl`, browser tools, or shell/network primitives into `packages/supervisor-core`.
- **Untyped payload blobs:** do not replace rag-only contracts with `dict[str, object]` or runtime-native request objects.
- **Transitive dependency reliance:** do not omit `httpx` from the new package manifest just because other packages already depend on it.
- **API-first widening:** do not force `apps/supervisor-api` changes into this phase if direct `supervisor-core` verification already proves the internal path.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTTP probe transport | raw `socket`, subprocess `curl`, ad-hoc `urllib` wrapper | `httpx.Client` | You need connection reuse, explicit redirect policy, timeout control, exception taxonomy, and test transports. |
| Redirect handling | custom 3xx-follow logic | `httpx` response history + `follow_redirects` policy | HTTPX already exposes redirect control and final URL semantics. |
| Timeout/error taxonomy | message-string parsing as the primary contract | `httpx.TimeoutException`, `ConnectError`, `TooManyRedirects`, and stable observation enums | The public contract should freeze stable observation semantics, not internal traceback text. |
| HTTP unit test harness | live network calls or deep monkeypatching of internals | `httpx.MockTransport` | Deterministic, fast, no network dependency, aligns with official HTTPX testing primitives. |
| Shared contract generalization | untyped dict payloads or retrieval-field abuse | explicit dataclasses + `Literal` discriminants in `packages/contracts` | Keeps the handoff machine-checkable and runtime-neutral. |

**Key insight:** the hard part here is not sending one HTTP request. The hard part is freezing the right boundary so a second specialist can exist without dragging HTTP/network semantics back into supervisor or polluting retrieval contracts.

## Common Pitfalls

### Pitfall 1: Redirects Are Not Followed Unless You Opt In
**What goes wrong:** the specialist records a 301/302 as the terminal result and never captures the final URL.
**Why it happens:** HTTPX does not follow redirects by default.
**How to avoid:** choose an explicit redirect policy for the specialist and persist both terminal URL and redirect chain semantics.
**Warning signs:** tests pass for 200 targets but lose `final_url` or misclassify known redirecting official sites.

### Pitfall 2: `raise_for_status()` Collapses Site-State Into Exceptions
**What goes wrong:** 4xx/5xx responses become execution errors instead of successful observations.
**Why it happens:** `HTTPStatusError` is only raised when code calls `raise_for_status()`.
**How to avoid:** inspect `response.status_code` and `response.history` directly for probe semantics; reserve `error` for malformed/config/internal failures.
**Warning signs:** 503 or 404 allowlisted targets come back as `error` instead of `completed` with typed observation data.

### Pitfall 3: TLS Verification Gets Disabled To “Make Probes Pass”
**What goes wrong:** the specialist hides certificate problems and reports false positives.
**Why it happens:** developers shortcut around SSL errors by setting `verify=False`.
**How to avoid:** keep TLS verification enabled by default; treat TLS failures as observations or operator config issues, not as something to bypass silently.
**Warning signs:** code adds global `verify=False` or custom insecure SSL contexts with no documented operator reason.

### Pitfall 4: Rag-Only Supervisor Assumptions Leak Everywhere
**What goes wrong:** contracts, context, routing, audit, and response code all keep `DelegateToRagAgent*` naming and single-target assumptions, so the new specialist lands as a special case or compatibility hack.
**Why it happens:** the current implementation hardcodes one request type, one response type, and one delegate callable.
**How to avoid:** generalize the shared envelope and dispatch boundary first, then implement `availability-specialist` against that shape.
**Warning signs:** new code adds `if availability ... else rag ...` branches in multiple files instead of one explicit routing/dispatch seam.

### Pitfall 5: Live Network Tests Sneak Into Unit Coverage
**What goes wrong:** tests become flaky, slow, and dependent on real external sites.
**Why it happens:** availability work feels “real” only when it hits a real host.
**How to avoid:** keep unit tests on `MockTransport`; put any live smoke proof in a separate, clearly optional eval/smoke slice.
**Warning signs:** test failures vary by local network, VPN, DNS, or current site uptime.

### Pitfall 6: Failure Granularity Is Over-Frozen Too Early
**What goes wrong:** the public contract promises exact DNS-vs-TLS-vs-TCP parsing before the implementation proves those distinctions are stable across environments.
**Why it happens:** HTTP transport libraries expose stable error families, but finer-grained cause details may vary by underlying stack.
**How to avoid:** freeze a small stable enum first and add detail fields only after tests pin the behavior.
**Warning signs:** contract review debates exact low-level error strings or platform-specific exception messages.

import httpx

timeout = httpx.Timeout(5.0, connect=2.0)

### Deterministic Probe Test With `MockTransport`
```python
import httpx

def handler(request: httpx.Request) -> httpx.Response:
    return httpx.Response(
        503,
        request=request,
        headers={"location": "https://status.example.edu/maintenance"},
    )

transport = httpx.MockTransport(handler)

with httpx.Client(transport=transport, follow_redirects=False) as client:
    response = client.get("https://www.example.edu/")
    assert response.status_code == 503
```
Source: [HTTPX Transports](https://www.python-httpx.org/advanced/transports/)

### Mapping Observation Semantics Without `raise_for_status()`
```python
def map_probe(target_id: str, client: httpx.Client) -> AvailabilityResult:
    try:
        response = client.get(resolve_url(target_id))
    except httpx.TimeoutException as exc:
        return AvailabilityResult(target_id=target_id, observed_status="timeout", detail=str(exc))
    except httpx.ConnectError as exc:
        return AvailabilityResult(target_id=target_id, observed_status="connect_failure", detail=str(exc))
    except httpx.TooManyRedirects as exc:
        return AvailabilityResult(target_id=target_id, observed_status="redirect_loop", detail=str(exc))

    return AvailabilityResult(
        target_id=target_id,
        observed_status="ok" if 200 <= response.status_code < 400 else "http_error",
        http_status=response.status_code,
        final_url=str(response.url),
    )
```
Source: [HTTPX Exceptions](https://www.python-httpx.org/exceptions/), Phase 03.1 context terminal-semantics rules

## Open Questions

1. **Envelope vs. parallel request/response pairs**
   - What we know: the contract must remain explicit, typed, and runtime-neutral.
   - What's unclear: whether the repo wants one generic envelope with specialist payload/result unions, or parallel `DelegateToRag...` / `DelegateToAvailability...` pairs behind a union alias.
   - Recommendation: use one shared envelope plus specialist-specific payload/result dataclasses; it minimizes churn in `context.py`, `routing.py`, `audit.py`, and later API wiring.

2. **How fine-grained should `failure_classification` be in v1 of this specialist?**
   - What we know: timeout, redirect, and transport-failure families are stable enough to model now.
   - What's unclear: whether DNS-vs-TLS-vs-other-connect subtyping is stable enough across environments to freeze as public enum values immediately.
   - Recommendation: freeze a small stable enum first (`ok`, `redirected`, `http_error`, `timeout`, `connect_failure`, `redirect_loop`), then add finer categories only if implementation tests prove they are stable.

3. **Should `apps/supervisor-api` expose availability requests in this phase?**
   - What we know: the phase can prove internal closure through `supervisor-core` tests without changing the transport shell.
   - What's unclear: whether the planner wants a tiny HTTP-level smoke path immediately or wants API widening deferred until handbook mainline work catches up.
   - Recommendation: keep API changes optional for Phase 03.1; only widen the HTTP shell if a smoke/eval requirement truly needs it.
