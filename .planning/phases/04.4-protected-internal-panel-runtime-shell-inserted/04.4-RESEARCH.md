## Summary

Phase 04.4 should freeze what the protected panel is as a repo/runtime shape, not what the panel does as a product.

The clean shape is:

- protected panel is a future `apps/` shell
- it consumes runtime APIs only
- it remains separate from `apps/supervisor-api`
- its protected/fail-closed posture is treated as a runtime and delivery assumption, not a package concern

The phase should explicitly say:

- where the panel belongs in the repo shape
- what the allowed runtime API seam means
- what kinds of coupling are forbidden
- what remains deferred to Phase 5 and to later product/UI work

**Primary recommendation:** make this a two-artifact phase: one canonical architecture note under `docs/architecture/`, plus one implementation handoff note under `.planning/`.

2. The panel is not a mode of `apps/supervisor-api`.

4. Fail-closed assumptions are part of the runtime shell boundary.
5. UI/business workflow scope remains deferred.
