# 代码组织

## 文档边界

本文规定顶层目录、模块所有权、重复治理和测试位置。它不维护当前文件清单，也不代替所属
模块的接口、架构或工作计划。

## 基本原则

一个模块应当有单一所有者、明确输入输出和靠近实现的测试。读者应能从路径和名称判断它
属于哪个应用、任务、领域或运行时。

以下形态不应存在：

- 只为降低文件行数而拆出的薄包装；
- 混合多个领域的 `utils`、`helpers` 或 `common` 目录；
- 同时服务多个应用却没有明确所有者的业务模块；
- 必须阅读整条调用链才能理解职责的转发层；
- 为临时验证保留的第二条执行路径。

## 顶层目录

- `apps/`：常驻应用、Cloudflare Worker、服务进程和浏览器界面；
- `jobs/`：需要独立构建或调度的一次性、定时任务；
- `packages/`：稳定合同、领域逻辑和可复用库；
- `scripts/`：仓库级开发、验证和部署入口。

进入 `jobs/` 的任务必须有独立入口、输入、失败语义和验证方式。只在本地使用的辅助命令应
留在 `scripts/` 或所属模块的 `scripts/` 中。

`packages/` 不拥有服务启动、队列消费、数据库连接或部署环境读取。Temporal worker、采集器、
数据库客户端生命周期和供应商 HTTP 客户端属于使用它们的应用或任务。共享包只暴露合同、
DTO、接口和不依赖运行环境的逻辑。

`packages/contracts` 不能依赖供应商、向量库、对象存储或框架类型。跨语言合同优先使用
JSON Schema 或 OpenAPI，语言本地类型不能成为第二份合同。

## 领域所有权

- 领域判断留在所属领域，不复制到每个消费应用；
- 传输、鉴权和页面组合留在应用边界，不下沉到领域包；
- 测试数据、schema 和脚本应能追溯到被验证的所有者；
- 公共辅助函数只有在确实服务多个调用方且不携带业务所有权时才进入共享包。

目录整齐不能代替边界正确。拆分时先恢复所有权，再考虑文件大小和命名对称。

## 重复治理

同一概念只能有一个可执行所有者。以下重复必须归并：

- DTO、schema、路由分类或环境变量规则在多个模块手写；
- 同一业务判断、鉴权规则或查询准入在多个消费层实现；
- 同一发布或测试准备逻辑在多个脚本分叉；
- 同一名称表、别名表或分类表由多个位置各自维护。

只有下列情况可以保留相似实现：

- 共享代码会泄露另一运行时不应依赖的类型或依赖；
- fixture 为了测试隔离而复制，并明确指向规范来源；
- README 只提供链接，不复制所有者正文。

出现第三处同类实现前，必须先确定唯一所有者。不得用兼容层、猜测补齐或静默成功掩盖
错误边界。

## 测试位置

- TypeScript 包的单元、合同和 schema 测试放在所属包的 `test/`；
- 应用级路由和集成测试放在所属应用；
- Python 测试只服务仍在使用的 Python 包；
- 不使用隐藏测试发现范围的 `load_tests` 聚合或通配导入；
- 中央静态检查只负责通用格式和文本卫生，领域不变量由所有者测试证明。

## 审查要点

结构性改动至少检查：

- 新目录和文件是否有明确所有者；
- 输入输出是否由合同或接口说明；
- 是否出现新的重复事实或第二条执行路径；
- 应用依赖是否被错误下沉到共享包；
- 测试是否靠近真正的行为所有者。

`pnpm repo:static` 不能证明这些结构约束。结构正确性需要结合代码、所有者测试和实际改动
评审。
