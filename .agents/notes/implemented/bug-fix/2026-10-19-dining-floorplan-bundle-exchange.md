# Agent Note: 食堂地图 bundle 草稿导入导出

Status: implemented

## 背景

本地地图标注需要迁移到另一套 Ops Web 环境。地图的持久事实是数据库中的完整全局草稿，发布版本由独立的
release 和 publication 管理；bootstrap 文件只负责空环境初始化。原有编辑器可以保存和发布画布，但没有
可校验的文件交换入口，手工重做会丢失整份地图，直接改数据库又绕过现有草稿、发布和对象存储 owner。

## 决策

使用规范化 `DiningFloorplanBundleV1` JSON 作为唯一交换格式。导出只读取当前已保存的完整全局草稿，导入
只接受 UTF-8、大小不超过现有草稿请求上限且通过 bundle 合同和地图诊断的文件。导入按全局 bundle 整份替换
草稿，不做按食堂隐式合并；确认框显示 hall、楼层和窗口数量并明确替换范围。

导入复用既有 `PUT /api/ops/dining/draft`、`expectedRevision` 和服务端 canonicalize。保存成功后编辑器按服务端
返回的 bundle 重建所有页面和形状，清除未保存状态；导入不调用 publish。学生端只有维护人员随后显式确认发布，
继续经过窗口引用检查、SVG 对象存储写入、release 创建和 publication 切换。

## 未采用方案

- 继续手工重做地图：不需要新增接口，但迁移成本高且容易遗漏全局楼层和窗口，不能满足本地标注交接。
- 直接提交或覆盖 bootstrap JSON：只影响空环境初始化，不能更新已有草稿，也会混淆初始化资产与维护数据。
- 通过数据库直写或临时 Kubernetes Job 搬运：绕过 revision、领域校验和发布 owner，无法保证工作台看到的草稿与
  发布链路一致。
- 按食堂自动合并：需要定义 ID 冲突和删除语义；当前合同是全局 bundle 且需求接受整份替换，因此不引入新的合并机制。
- 导入 SVG 或 tldraw 原始文档：这些是发布产物或编辑器内部格式，不包含可复用的领域 bundle 合同。

## 后果

维护人员可以在本地和目标工作台之间传递已保存地图，导入失败不会触发发布，未发布前学生端版本不变。整份替换
要求操作人员在确认前核对文件范围；revision 冲突要求刷新后重新导入。文件大小限制与现有草稿接口保持一致，后续
若 bundle 合同或请求上限变化，交换入口和服务端常量必须同步更新。浏览器回归使用本地 fixture；本地环境缺少
Playwright Chromium 时不能执行该用例，线上导入与发布仍是独立的人工操作。
