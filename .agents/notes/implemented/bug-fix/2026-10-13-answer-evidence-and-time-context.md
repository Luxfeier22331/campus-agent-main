# Agent Note: 回答证据与时间上下文

Status: implemented

## 背景

恢复合成将同一通知、同一章节的不同片段误认为重复。联系方式、附件名单、选题要求可以分布在同一章节的
不同块中；以章节为键会删掉已经检索成功、仍影响用户答案的材料。仅覆盖不同通知同标题的测试无法发现这一缺陷。

工具层已有基于冻结 run 创建时间的相对年份转换，但模型未获得该时间，可能在生成检索词时把“去年”改写为
“往年”，使精确转换无法命中。恢复合成也缺少同一时间基准。

Gemini 单次 model turn 在 JSON 解析失败时只保存通用错误码，绕过已有 ModelOutputError 诊断。
旧 Runner 的测试不能证明 Temporal 使用的单次调用会把诊断送到 Control 投影。

## 决策

- 合成输入复用既有按 evidence ID 去重的逻辑，删除章节级去重。同一证据仍只传一次，不同证据不因同章节而丢失。
  本项部分取代[检索结果多样性与合成输入去重](../architecture/2026-09-29-search-result-diversity.md)的合成输入规则，
  不改变检索选段与每次返回预算。
- Activity hydrate 将既有 StageRecord 的冻结创建时间交给模型，各阶段通过 operation data 的 requestTime 使用同一
  基准解释相对年份。保留用户原话，不以 Activity 当前时间或 deadline 推断年份，也不新增持久化字段或跨服务合同。
  延续[通知发布时间证据与相对年份查询](./2026-09-30-notice-publication-evidence-and-relative-years.md)对发布时间和适用年度的区分。
- Gemini 单次调用复用 failedRunnerResult 保存有界原始输出与 JSON 解析诊断，沿已有 Control/Ops 合同传递。
  诊断不进入恢复合成材料或用户正文；继续拒绝非法 JSON，不从异常响应截取看似可用的前半段。

## 未采用方案

- 将正文加进章节去重键可以减少误删，但工具已按 result_ref 排除重复片段，合成前又按证据 ID 去重，
  没有必要维护第二套内容身份规则。
- 只在工具层补年份无需改变模型上下文，但无法恢复被模型泛化掉的时间意图，也不能约束恢复合成的年度选择。
- 重新启用供应商输出 Schema 或 JSON MIME 有可能约束格式，但与既有通道的工具组合存在已观察到的兼容性问题；
  保持[模型调用兼容性](../architecture/2026-10-10-json-output-streaming-transport.md)的约束，不以自动修补或重试掩盖异常输出。

## 后果

合成器保留更多互补片段，输入可能比章节级去重时长；这是保留真实证据的必要成本。来源编号和原始证据身份不变。
回归覆盖同章节的不同片段、同证据重复输入、Solve 与 Synthesize 的时间上下文，以及真实 SDK 模拟流响应经
Activity 到 Control 的格式错误诊断。测试使用合成内容，不复制用户会话或供应商异常正文。

本地回归不能证明供应商不再输出无关内容，也不能证明模型一定按目标年度检索；这些效果仍需在实际模型通道验证。
本改动不把产品终态 completed 等同于模型首次执行成功，不承诺固定的端到端耗时降幅。
