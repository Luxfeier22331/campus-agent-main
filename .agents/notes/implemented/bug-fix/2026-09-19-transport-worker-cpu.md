# Agent Note: 班车公开查询的缓存与计算成本

Status: implemented

## 背景

班车查询出现 Worker CPU 超限。Campus 请求携带 `include=notices`，边缘缓存却只接受日期参数，
导致实际页面请求绕过缓存；月历在 Worker 内重复选择时间段、整理下一运行日边界和校验逐日响应。
已有缓存测试使用不带通知的 URL，没有覆盖页面实际请求。

## 决策

- App API 保持 Cloudflare Worker。先修正缓存和查询成本并测量，不新增 Node 入口或 read 镜像。
- Transport 包提供不依赖 schema 的公开 URL 构造与缓存规范化入口；Campus 请求和边缘缓存共同消费。
  通知变体单独缓存，未知或重复参数继续交给原 API；错误、私有及带 Cookie 写入的响应不共享。
- App API 一次关联读取班次事实，排除已结束的历史时间段，保留下一运行日需要的未来时间段。
  通知只为实际返回的时间段批量读取；不带通知时不执行通知查询。
- 时间段选择与下一运行日的中间结果只在一次请求内复用，避免引入需要失效协调的业务缓存。
  输入事实保留校验，范围输出只校验一次；公共路由诊断的匹配器在初始化时编译。
- 新增查询验证进入既有 PostgreSQL 集成测试；缓存回归使用页面的真实 URL 构造函数。
  性能测量按需执行，不新增浏览器 smoke 命令或依赖机器计时的 PR 门禁。

## 未采用方案

- 集群 Node read 服务能够移出 Worker 计算，但 App API 已固定使用 Worker；先优化和测量，
  只有实际 miss 路径仍无法满足预算时，才重新讨论额外部署边界。
- 开启整个 Hyperdrive 的查询缓存能减少部分读取，但同一绑定服务产品读写；不改变其现有新鲜度合同。
- 只修缓存可以降低总调用量，但不能降低冷请求和缓存过期后的单次计算成本，因此同时优化查询与投影。

## 后果

公开接口字段、排班优先级、停运、下一运行日与通知展示语义保持一致，数据库结构不变。
缓存与原始事实的所有权仍分别在 Campus 边缘代理和原产品数据模块。
本地 workerd 进程 CPU 测量用于比较改动，不替代 Cloudflare 计费 CPU，也不证明部署后的预算已达标。
