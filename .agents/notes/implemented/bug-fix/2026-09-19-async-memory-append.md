# Agent Note: 异步记忆追加

Status: implemented

## 背景

staging 的回答已经成功，但外层 90 秒请求超时后 Hindsight 仍在处理，Temporal 重试又提交了同一消息。
模型提取约 140–210 秒后完成，说明 HTTP 等待结束不能证明后台任务已经失败或停止。
用户要求区分模型请求超时与后续写入耗时；模型失败可重试，写入进行中继续等待。

## 决策

使用当前 Hindsight 的 async retain 与调用方 operation_id 去重；每个 bank/generation/message
对应稳定任务身份，提交确认丢失时重提也只返回原任务。独立 Temporal 子工作流在回答完成后跟踪它，
提交和状态查询采用短 Activity，间隔通过 Workflow timer 等待。

模型单次请求期限设为 300 秒，Hindsight 继续拥有模型与任务内部重试。远端明确最终失败后，
外层记录失败，不再重新执行；连接中断、not_found 或状态未知不是重新创建任务的依据。
保留供应商原有整项任务保护，不在产品侧复制提取、向量化和 consolidation 调度。

复用现有调用登记表：append 可以无到期登记，直到任务终态投影成功才释放。
完整清除和账号注销是其真实消费者，必须等待原任务结束；普通读取仍使用原有租约。
仅查询业务任务终态，不建设供应商内部进度镜像。

本决策部分取代 [Hindsight 记忆生命周期](../architecture/2026-07-17-hindsight-lifecycle.md)
中的同步追加及外层执行重试方式，其内容所有权、管理操作和清除范围继续有效。

## 未采用方案

- 仅把同步 HTTP 期限延长到 300 秒：改动小，但断连和慢写入仍会产生执行结果未知，不能避免重复处理。
- 取消正在执行的 retain 后重试：符合直观顺序，但当前供应商只支持取消 pending，断开 HTTP 不取消 retain。
- 禁止所有重试：可以减少外层重复提交，却失去提交确认与查询的恢复能力，也不符合用户要求。

## 后果

新增一个后台 Workflow 和最小 schema 迁移；需要先迁移再发布运行时。Hindsight 不可达或 operation
状态未知时，清除会继续等待，不能把查询失败视为排空。已存在的任务状态是唯一完成依据。
若未来供应商提供等价的完成通知，可重新评估轮询；不能因此放弃稳定任务身份和清除保护。

同步执行代码仅保留给旧 Temporal 历史重放，待旧执行结束且历史超过保留期后删除。
验证覆盖响应丢失、查询中断、长时间写入、明确失败、终态重复处理与清除竞争。
