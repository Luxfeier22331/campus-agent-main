# Agent Note: 通知正文图片独立消费

Status: implemented

## 背景

通知正文中的图片承载可检索信息，原有 OCR 仅自动选择特定班车标题，通知索引只读取正文文本，
因此纯图片通知无法进入检索。用户要求先处理正文图片，OCR 文字用于 embedding，并允许 Ops 查看；
每次 embedding 必须照常处理通知，不等待图片识别成功。

## 决策

正文图片复用现有 OCR 任务和页面存储，由 `jobs/document-ocr` 独立扫描所有已采集站内通知；
分类和发布不作为识别前提。附件不纳入本次消费，外链不扫描；图片选择复用通知领域清洗规则。
JPEG/PNG 原样上传，GIF 首帧、BMP 转为 PNG；来源对象不改写，输入摘要按原始字节计算。
来源序号用于对象定位，展示序号用于 Ops 正文对应关系，二者分别保存。

`jobs/notice-index-publisher` 的来源适配在同一只读快照中，将正文和当时已保存的图片识别文本组装成
分块输入。每张图按已发布资产摘要匹配同通知的 OCR 输入摘要，使用最新完成批次，按已发布图片序号和页序追加文字及表格，移除 OCR 图片引用。
来源快照更新、资源去重及发布边界见[通知同 ID 更新与重新发布](../architecture/2026-10-02-notice-republication-and-updates.md)。
未识别、失败、运行中均不作为排除通知的条件；没有正文或 OCR 文本时使用标题。
后续完成的 OCR 在下一次构建生效，Chunk / Embedding 消费者只接收文本，不接收任务状态或触发 OCR。
不增加 embedding 消费标记，不等待全部图片完成，也不因 OCR 未完成而保留旧索引。

Ops 通知维护页逐图查看原图、状态、结果及执行识别、恢复、重识别；公众通知正文合同保持不变。
该读取方式使用现有任务与页面表，无需新的通知状态、派生表或跨系统任务编排。

Ops 图片列表按通知与来源对象分组，先选择最近 100 组，再读取组内历史；不能先截断最近 100 次尝试，
否则旧成功结果可能被重试挤出。通知详情与图片列表复用同一结果选择：最新尝试和最近成功结果分别显示，
后续失败不遮蔽已有成功文本。来源序号使用资源元数据，缺少时从通知来源解析，不从对象键推算。
OCR 调度启停沿用任务服务的只读投影，页面展示暂停不自动改变集群设置。

OCR 结果弹窗共用阅读组件。供应商在 HTML 表格文本中输出的字面量换行和箭头表达只在渲染树中转换，
不全局反转义，不修改数据库 Markdown，也不改变 embedding 的来源文本。

## 未采用方案

等待所有图片识别后才构建可以得到一次完整内容，但会让单图失败阻塞通知，违背已确认的消费规则。
完全不读取 OCR 能使两条链路互不依赖，却丢失本次图片消费的检索目的。
将 OCR 写回公开正文可复用现有读取路径，但改变面向学生的通知展示合同；因此在索引来源处组装。

## 后果

一次索引构建可能只有部分图片文字；下一次构建读取新增结果，无需 OCR 主动触发 embedding。
图片文本按图片顺序附在正文后，当前不重建其在 HTML 段落之间的位置，原图布局仍由通知展示负责。
GIF 只消费首帧。附件扩展需要另行确认，不通过现有 PDF 上传或历史任务能力自动扩大扫描范围。
独立 CronJob 沿用既有部署启停方式，Ops 手动识别复用现有启动入口。

- 图片聚合使用真实 PostgreSQL 集成测试验证：同一图片在成功后连续失败 105 次，最近图片列表仍保留旧成功结果；不同通知不会因来源对象相同而混合历史。接口测试验证当前结果与最新失败分别输出，浏览器验证表格换行与箭头显示、页码跳转及通知返回。OCR 包单元测试 22 项通过，embedding 合同未改动。
