# Agent Note: 定时任务治理与通知索引自动刷新

Status: implemented

## 背景

用户确认自动采集、分类、发布与通知索引刷新需要形成完整链路。当前分类和发布依赖手动运行，
索引保持发布时快照；Ops 需要统一查看运行结果并管理启停和周期。

## 决策

GitOps 管理任务代码、身份和资源；Ops 直接管理原生 CronJob 与 Temporal Schedule 的启停和周期。
分类、发布每 15 分钟运行，索引每 60 分钟刷新，资源首次创建暂停。分类和发布使用数据库会话锁，
单条数据错误持久化为当前处理问题，人工重试成功后清除；基础设施错误停止本轮。

索引 worker 复用公开构建接口，在独立 Temporal 队列执行，沿用当前 Docs embedding artifact，
刷新 Notice artifact。发布器统一管理版本、预期当前值激活、当前和上一版本保留及受保护清理。
Ops `/tasks` 展示运行状态、业务结果、问题数与调度设置，不引入独立调度数据库。

此决策部分调整 [Temporal 边界](./2026-06-06-temporal.md) 的离线任务范围；
在线执行职责不变。通知时间字段和图片附件内容消费由独立 issue 处理。

## 未采用方案

仅启用 CronJob 最容易部署，但无法承担索引各阶段的恢复与受保护版本生命周期。
统一迁移所有任务到 Temporal 可以减少调度类型，但会无必要地改写现有独立采集任务。
数据库复制调度设置便于历史查询，却会引入双重事实来源；直接使用原生设置即可满足当前消费者。

## 后果

自动通知经过分类、发布和索引刷新可被检索。并发入口互斥，坏数据不阻塞其他通知，人工修复可恢复。
索引中断、竞争发布及重复激活不破坏当前与上一版本，清理不删除受保护资源。
Ops 可查看真实结果并暂停、恢复、调整周期；GitOps 同步保持设置，资源重建默认暂停。

Schedule 的 action Workflow ID 会追加时间戳，因此由短入口工作流启动固定 ID 的刷新子工作流，
手动刷新与回滚直接竞争同一 ID；运行中冲突由 Temporal 原子拒绝，不能以 visibility 查询、
Schedule 暂停或单 Activity 并发数代替互斥。入口异常关闭时不终止子工作流，避免提前释放执行 ID；
正常取消等待 Activity 完成。保留发布器锁与 expected-current CAS，处理人工发布与活动重投递。

回滚由 Ops 一次查询已验证的上一版本，将 artifact 引用、来源与预期当前值写入 Workflow 输入；
Activity 重试不再读取“上一版本”。已激活目标的重试保持 no-op，过期目标不覆盖当前指针。
Ops 按 Temporal Run ID 标识每次执行，详情精确查询该次执行，不从最近二十条中寻找。

自动分类失败在通知行锁下检查 category 仍为空才记录问题。人工修改分类使用同一连接的
READ COMMITTED 事务，先更新分类再以新语句删除问题；后者能看到等待行锁期间提交的失败记录。
显式重新分类沿用分类操作族锁与覆盖语义，不把已分类通知的人工重试误判为自动跳过。

### 发布边界

发布器版本登记需要匹配真实的现有 artifact，不能用空引用跳过迁移。
清理只认领新增自动产物；现有手动产物保留。上线需先完成 schema 与精确字段忽略，再启用调度。

本地已验证真实 Schedule 的无变更跳过、通知变化后的 embedding 与 Qdrant 可检索、上一版本回滚；
工作流取消、worker 替换恢复及历史重放通过。数据库集成覆盖操作族互斥、分类问题恢复、发布逐条事务和
写入故障回滚；清理验证版本保护、对象删除顺序及失败重试。共享 derived writer 仅新增三类 Notice RAG
产物前缀的版本枚举和删除权限，缓存、来源资产仍不可删除。

部署前还需合并 Source 合同并发布真实镜像 digest，由 GitOps 普通拓扑变更加入 worker consumer；
精确忽略 schedule/suspend、schema 与对象存储权限须先协调。当前分支的本地验证不代表 staging 已部署，
定时端到端验收在该 revision 完成发布后执行。时间字段与附件消费继续留在 #532、#533。

本次修复发布需暂停 Schedule、停止旧入口的新请求并排空旧刷新与回滚，再更新 worker、Ops 和
Schedule action；旧的时间戳刷新 ID 不参与新的固定 ID 互斥。没有可回滚版本时返回 409 且不暂停，
启动冲突时保留暂停。修复回归覆盖真实 Schedule 冲突、回滚重投递和 history replay，
以及 PostgreSQL 双连接的失败先写入／人工先修复两种顺序。
