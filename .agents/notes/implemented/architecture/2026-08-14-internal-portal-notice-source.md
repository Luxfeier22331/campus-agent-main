# Agent Note: 内部门户通知来源合同

Status: implemented

## 背景

早期通知采集只请求类型 `5`，并在对象路径和每条来源对象中重复保存站点、类型名称和组织名称。
通知消费不按采集批次顺序执行，集群 source bucket 也没有需要迁移的历史通知对象。

校内门户与公开网站具有不同的身份、访问和采集语义。把两者视为同一来源会混合公开抓取策略
与依赖会话的内部采集，也会让来源事实和下游领域正文失去清晰边界。

## 决策

- 通知选择器确定采集范围，全局列表只提供跨类型增量顺序，不能用通知 ID 数值推断时间；
- 通知 ID 是对象身份，类型和组织 ID 属于对象字段，名称映射集中维护，不在路径和每条对象重复；
- 外链使用明确标记和来源 URL 表达，采集器不请求外部正文或建立外链抓取状态；
- 同步状态只保存增量与历史覆盖边界，已有合法对象不重复请求，不维护内容版本或 `captures/` 批次；
- 分类只确定唯一内部领域，不表示领域消费、对外发布或用户阅读完成，也不写回来源对象；
- 校内门户使用独立来源通道 `internal_portal`，与公开抓取通道分离；
- `notice` 与 `file_release` 是两个独立来源类型，不互相转换；
- 门户内容不按登录主体形成请求、产物、条目或发布流作用域；
- `jobs/internal-portal-collection` 只负责门户适配、来源对象和明确请求的文件发布，不负责通知
  规范化、文档分块、向量索引或在线发布，采集完成不自动发布；
- `jobs/internal-portal-collection` 不持久化 TGC；凭据持久化、检查与解析的当前所有权由
  [采集控制面与凭据所有权](../simplification/2026-08-19-internal-portal-credential-resolution.md)
  管理，本地命令只消费调用方显式提供或显式拉取的认证输入；
- 认证客户端负责会话建立、校验和错误分类，凭据解析由
  [采集控制面与凭据所有权](../simplification/2026-08-19-internal-portal-credential-resolution.md)
  管理，具体认证操作与同步步骤由数据文档和 runbook 维护。

## 未采用方案

- **在路径和每条来源对象中重复站点、类型与组织名称**：对象单独读取较直观，但重复维护可变名称。
- **按批次或通知 ID 数值推断采集顺序**：便于枚举任务，却不能表达跨类型的真实时间边界。
- **合并公开抓取与门户采集通道**：能共享入口，但会混合依赖会话的认证语义与公开抓取策略。
- **采集完成后直接开放在线检索**：缩短处理链路，却绕过规范化、领域校验和独立发布边界。

## 后果

本篇保留通知来源身份、外链不抓正文以及采集不等于发布的边界。后续规范化存储由
[规范化通知存储](./2026-08-14-normalized-notice-storage.md)定义；
[通知维护状态收敛](./2026-08-25-notice-maintenance-state.md)进一步让采集登记数据库库存、分类写回
通知行并显式发布，也维护当前同步区间合同。因此“采集只写来源对象”的历史范围已被扩展，不能
据此跳过数据库登记；来源对象仍不被分类结果改写。

- 认证成功或采集完成不代表通知已经具备在线查询能力；
- 来源对象和规范化通知分别由各自的数据所有者维护；
- 下游规章、校历等领域必须经过自己的校验和发布入口消费通知来源；
- 不把通知采集、认证检查或来源文件发布隐式接入在线检索链路。
