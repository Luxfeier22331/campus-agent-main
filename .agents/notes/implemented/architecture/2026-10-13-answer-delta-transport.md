# Agent Note: 临时回答传输与持久运行状态分离

Status: implemented

## 背景

Runtime 的模型 Activity 已与 Control API 分开运行。逐段正文原先调用 Control 写入运行事件表，
浏览器再从持久事件读取正文；每个短片段都需要事件事务，而产品最终答案已有独立持久投影。
旧草稿只删除写库并增加单进程缓冲，没有连接跨进程消费者，也不适用于多个 Control 副本。

## 决策

Runtime 保持模型与工具编排所有权，通过 typed API 发布正文；Control 拥有临时传输及有界缓冲。
复用 Control 已使用的 PostgreSQL LISTEN/NOTIFY 广播到在线副本，不新增 broker、部署凭据或实例路由。
通知正文受单条载荷上限约束，两个生产者均按 Unicode codepoint 分片。广播仅承载临时正文，不代替持久结果。

Runtime 先调用独立的 `answer/started`，Control 的幂等开始事务仅写 streaming 状态及 answer_started。正文从事件表移除，完成事件、产品终态与
最终答案保持持久化。App API 复用原长轮询路径，把临时正文转换为浏览器 SSE；读取持久历史不混入临时数据。
同页中的增量在终态之前输出，持久事件之间的顺序保持不变。

开始与完成投影必须成功；临时发布不承担持久状态变更。Runtime 临时投递使用单次一秒预算，
遇到网络、超时或可重试服务错误后停止本次模型调用的其余草稿发送，继续保存最终结果。
取消与执行期限优先，认证和合同错误不能被当成临时失败。buffered 发布采用相同失败隔离，
且总临时发布预算为一秒。PG 发布不依赖发布进程自身的 LISTEN 连接。

读取临时正文失败不丢弃已查到的持久事件；监听故障后重新查询持久结果，并保持剩余长轮询等待预算，
避免故障期间空转。后续请求复用现有监听重建机制，不新增投递重试队列或后台恢复循环。

正文使用独立的 answerIndex，不能冒充持久事件身份或推进 sequence。浏览器续传携带两个游标，
重复正文按 answerIndex 丢弃；缓冲不完整时继续接收后续增量，最终由会话消息替换草稿。
这部分取代[回答传输模式](./2026-09-28-answer-transport-stream-buffered.md)中将单个全文增量持久投影的决定，
模型 stream/buffered 选择和最终答案的权威地位仍有效。

## 未采用方案

- 仅用进程内缓冲：实现最少，但发布请求与订阅可能进入不同 Control 副本，无法完成当前部署下的交付。
- 引入 Redis 或 NATS：可提供专用广播能力，但当前已有 PostgreSQL 通知监听，没有增加另一套部署的必要。
- Runtime 直接连接浏览器或持有产品投递凭据：可减少一跳，但破坏现有 Worker 入口与 Runtime 执行边界。
- 内部改成长连接 SSE：可以减少长轮询请求，但移除正文持久化不依赖这一变更；先沿用已部署的入口与传输。

## 后果

正文片段不再产生运行事件行及对应行锁事务；PostgreSQL 仍承载临时通知，模型调用也仍通过 Control API。
内存按 run、字节、段数及总 run 数限制，闲置缓冲在后续访问时过期。它不是可完整重放的日志：
监听断开、实例重启和缓冲淘汰可能丢失草稿片段，最终结果通过原持久链路恢复。

状态读取和临时正文的游标独立；后续扩展必须保留这一语义。若实际规模证明通知吞吐或广播开销成为瓶颈，
可替换传输实现，不能把持久结果恢复责任移到临时通道。真实 PostgreSQL 双实例测试覆盖广播、重连与正文不落表，
前端与 App API 测试覆盖游标独立、重复片段和终态处理。端到端套件连接真实 Temporal、Runtime、
双 Control 与 Worker，覆盖断线、副本重启和发布不可用，并在刷新后读取持久答案；可控模型响应
用于稳定注入故障，真实 provider 验收单独启用，二者不能互相替代。
