# Agent Note: 镜像逐个构建与 Runner 并发配置

Status: implemented

## 背景

镜像发布将同组目标一次提交给 Bake，heavy 与 standard 之间串行不能约束组内目标。
源码工作流只为 hosted builder 配置了内部并发限制，自托管 builder 的配置缺少对应限制。
已有 builder 不会重新读取宿主机配置，原能力探针也没有检查节点的并发配置。

## 决策

PR 镜像检查与候选发布共用逐镜像执行路径，保留 heavy、standard 分组与原排序。每次只提交
一个目标，并等待构建、导出及发布 metadata 读取结束后继续。各镜像独立保存构建结果，
分组墙钟时间只计一次。失败后停止，已完成结果保留，后续目标保持未开始。

自托管 builder 与 hosted builder 都使用 `[worker.oci] max-parallelism = 2`；能力探针读取
Buildx 注册节点的配置，而非宿主机文件。主机侧配置由现有 Runner 运维入口维护，保留缓存应用变更，
操作步骤由 [Runner 手册](../../../../docs/runbooks/runner-buildkit.md) 维护。

继续使用既有镜像缓存与不可变制品复用。缓存导出 warning 不阻断正式镜像发布，镜像推送失败
继续阻断发布。完整 digest 集合仍只在所有选中制品完成后写出。

## 未采用方案

- 只限制 builder 内部并发，改动较小，但仍会同时提交多个镜像；恢复逐镜像执行符合现有串行资源约束。
- 增加资源或延长心跳期限可能减少失败，但当前没有故障时段采样证明所需容量，也不能修复配置遗漏。
- 自动重试可能恢复偶发发布，但会掩盖会话失效；本次保持原始失败，并在实际复验时采集资源压力。
- 清空缓存能建立冷构建基线，但会增加恢复开销，无法解释已有会话失效，不作为修复步骤。

## 后果

镜像之间不再同时执行，代价是失去同批多目标调度。缓存继续复用，共享层不要求重新编译。
回归测试验证等待前一目标结束、失败后停止、独立 metadata、缓存 warning 和配置遗漏检测。
会话心跳失效已被日志确认，资源压力是待验证解释；构建通过不等于已证明最终根因。
